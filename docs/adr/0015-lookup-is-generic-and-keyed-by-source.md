# Lookup is one generic field type, keyed by Source

A `lookup` Field stores exactly one id from an external **Source** the Consumer registers. A Consumer declares a Field naming a Source, registers one adapter function under that name, and has a working picker — no new component, no new field type, and nothing to change in fieldkit per collection. The Sources live on the adapter surface as `lookup?: Record<string, LookupSource>`, keyed by the id a Field's `source` setting names.

This is deliberately **not** a Reference. The glossary defines a Reference as a pointer from the Content being edited to another **Content**, and the motivating case — a layout stylesheet — is not one: it lives in another service and another database, has no Blueprint, no Versions and no Releases, and therefore nothing to pin to. Calling it a Reference would put a `pin_mode` setting and a Pin select on a value that can never have either.

**A record, where every other key on the adapters object is an object of functions.** That shape is the decision. Adding a Source is then purely additive for a Consumer — a key, with nothing in fieldkit to change and no other Source to disturb; fieldkit can tell "no Source registered under that id" from "the Source found nothing" and degrade with a message naming the id; and each Source is independently testable. Adding `lookup` to the adapter surface at all is within [ADR-0002](0002-generic-catalogue-domain-types-belong-to-consumers.md), which states that the *catalogue* is generic while the *integration surface* is not — and here even the surface stays generic, because fieldkit never learns what a Source holds.

**The stored value is a bare id string**, following `media` rather than `single_reference`. A media pointer stores a plain id because it carries nothing about the pointing; a Reference stores an object because it carries a Pin and Attributes. A Lookup carries neither.

**Single-only.** A list variant would produce `string[]` where this produces `string`, which is exactly the reasoning [ADR-0005](0005-list-is-its-own-type-not-an-array-mode.md) gives for Single Reference being its own type rather than a capped Reference. One can be minted later if something needs it.

The control is anker's `LookupSelect` and nothing else. Debounce, menu-open gating, request cancellation, the stale-answer guard, page accumulation, loading and failure presentation, and the resolved → just-picked → raw-id label chain all belong to the atom (anker ADR-0002, "atoms may orchestrate async"). What is left in `LookupField` is the half the atom deliberately does not have: finding the Source, adapting between the two paging vocabularies, and reporting a failure on the Consumer's `onError`. There is no second async implementation, which is the point — `SingleReferenceField` is the first, hand-rolled against `BaseSelect`, and rebuilding it on the atom is its own ticket (knkCS/fieldkit#183).

`resolveByIds` is optional on the same terms as every other optional adapter method ([ADR-0009](0009-reference-adapter-describes-itself-with-specs.md)): without it a stored id reads as the id, which is visibly degraded rather than blank and is what a Consumer who has not implemented resolution should get rather than an error.

## Considered options

**A per-entity adapter key** — `adapters.stylesheet`, `adapters.printer`, each with its own `search`/`fetch` pair, and a field type per entity. It is the shape the existing surface already has for `reference`, `media`, `blueprint` and `textType`, so it needs no new idea. It was rejected because it makes every new collection a fieldkit change: a new key on `FieldKitAdapters`, a new plugin, a new renderer, a new cell, a new settings editor, all of them identical apart from a string. That is the coupling ADR-0002 exists to prevent, arriving through the surface instead of through the catalogue.

**A Consumer-minted plugin**, the way [ADR-0010](0010-toc-reference-belongs-to-the-consumer.md) has a Consumer mint its own reference-shaped type through `createReferencePlugin`. It puts the Consumer in full control and costs fieldkit nothing but a factory. It was rejected because the two cases are not alike: ADR-0010's Consumer needed *different behaviour* — its own tree semantics — whereas every Lookup behaves identically and differs only in which collection it reads. A factory here would have every Consumer re-declaring the same plugin to vary one string, and the settings editor, the cell and the Zod type would be copied into each of them rather than maintained once.

**Mirroring the atom's own contract** — `search({ query, cursor, signal }) => { items, nextCursor }` — was the obvious way to avoid an adapter that translates. It was rejected because it would make `lookup` the only method on this surface that pages by cursor and the only one taking an `AbortSignal`: `ReferenceSearchQuery` asks in `page`/`page_size` and answers `{ items, total }`, and `reference.fetch` takes a bare `string[]`. A Consumer writing its second adapter should not meet a second vocabulary. Translating is four lines in `LookupField`, and it is fieldkit's job precisely because it is the layer that knows both sides. The cost is real and worth naming: fieldkit cannot pass the atom's `AbortSignal` on to a Source, so a superseded request is not *cancelled*, only discarded — the atom's request-id guard still makes a late answer for an old query unable to overwrite a fresh one, so correctness holds and only the courtesy is lost.

## Consequences

The anker peer range narrows from `^3.1.0 || ^4.0.0 || ^5.0.0` to `^5.1.0`, because `LookupSelect` first ships in anker 5.1.0. The devDependency is raised to `^5.1.0` in the same change, and only because of it: [ADR-0014](0014-compile-against-the-oldest-anker-we-promise.md) has fieldkit compile against the oldest anker it promises, and warns that raising the devDependency beside a wide range "reads as neglect, and the correction is the mistake". The rule is unchanged and still holds — `^5.1.0` *is* the oldest anker fieldkit promises, so the two moved together and stayed equal. Anything importing newer-only anker API still fails to compile here rather than at runtime in a Consumer.

This is a **breaking change** for any Consumer still on anker 3.x or 4.x: they will meet `ERESOLVE` at install, which is the loud failure ADR-0014 prefers to the silent one. It also retires the `^3.1.0` leg that ADR-0014 recorded as "defended by neither compiler nor evidence" — not as a decision of its own, but as a side effect of there being one supported major again.

`lookup` sits in the `selection` category, not `reference`. The type picker groups by category, and a Lookup listed among the Reference types would say it is one.

There is no `readComponent`. Read mode could reach the Source and show a label where the cell can only show an id, but doing so means a second implementation of the resolution `LookupSelect` already owns — the one thing this design is meant to avoid — so the cell renders the stored id in both places until there is a reason to build it properly.
