# A Field Type is defined once: its settings as data generated from TS, its values as code in both languages

contenthub ADR 0010 makes fieldkit the field-type system in TS and in Go. The two halves are split along the line between what is declarative and what is not. **Settings are data:** every plugin declares a strict Zod `settingsSchema`, and a build step emits the **Catalogue** — every type's id, settings JSON Schema, Positions, the settings keys that hold a Pin, whether it has text — as a committed JSON file that the npm package and the Go module both embed. Go's `ValidateSettings` is generic over the Catalogue, plus a small hand-written hook per type for rules across settings. **Values are logic:** `toZodType` is a function of the settings, so `ValidateValue`, `Edges`, `Compare`, `Merge` and `Text` are hand-written in Go, one file per type, and pinned to TS by shared conformance fixtures that Vitest and `go test` both run.

The Go module lives in `go/` as `github.com/knkcs/fieldkit/go`, with the opt-in publishing package at `…/go/publishing` beside `@knkcs/fieldkit/publishing`. **Both carry one version number:** a release pushes `vX.Y.Z` and `go/vX.Y.Z` from the same commit, both embedding the same Catalogue, so "does contenthub know everything this Blueprint Release uses" is a comparison, not a mapping. Fixtures live at the repo root in `conformance/<version>/`, outside both languages, and a released version's directory is never edited.

## Considered Options

- **Hand-written Go for everything, checked by fixtures.** Rejected for settings: Go rejects unknown keys and Blueprint Releases are frozen for ever, so settings are where drift costs most, and fixtures only catch drift where they happen to reach. knkeditor rejected the same option for the same reason (knkeditor ADR 0001).
- **Generating everything from TS.** Rejected: value rules are settings-dependent code, and could only be generated by rewriting every `toZodType` as data.
- **A separate Go repo, per-service Go, or field types inside versionkit.** Rejected on contenthub's map (contenthub ADR 0010): one type's definition split across two repos is how fieldkit and core drifted apart.
- **Separate version numbers for npm and Go.** Rejected: the gate would need a mapping table. The price accepted instead is that a TS-only release bumps the Go module too.

## Consequences

- TS gains the unknown-key rejection Go has, because both read the same schemas.
- `commons/fieldspec` stays in commons on raw JSON: it merges System Fields and knows nothing of types. fieldkit's `ValidateSpec` enforces the card-marker rule it relies on, so the two cannot disagree about a valid Spec.
- A type's settings form can be rendered from its `settingsSchema` alone. fieldkit renders one for any type without a `settingsComponent`, so every type — the publishing package's, or a Consumer's — is configurable from its first release.
