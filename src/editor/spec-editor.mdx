# SpecEditor

A WYSIWYG editor for `Field[]` specifications: authors add, arrange, and
configure fields directly on a live preview of the form they're building, in
a **Build** mode, then flip to a **Preview** mode (label key `tryIt` — the
key predates the 0.9.0 rename) to fill out and submit the real thing.
`SpecEditor` owns an internal draft session (see
[The Draft Model](#the-draft-model)) and commits it back to the host only
when the author clicks Save.

## When to Use

Reach for `SpecEditor` anywhere an admin authors or edits a content type,
form, or record schema — it is the write side that pairs with
[SpecForm](?path=/story/renderer-specform--horizontal) (the read/fill side).
`TypePicker` stays exported for hosts that need the bare field-type picker
UI outside the ⊕ insertion popover (for example, a custom "add field" flow);
most consumers won't need it directly.

## Props

| Prop            | Type                                | Default | Description                                                                 |
|-----------------|--------------------------------------|---------|-------------------------------------------------------------------------------|
| `schema`        | `Schema`                             | —       | The **committed** specification. See the schema-prop stability contract below. |
| `onCommit`      | `(schema: Schema) => void \| Promise<void>` | —  | Called with the draft when the author clicks Save. May return a Promise; a rejection surfaces an error toast and keeps the draft dirty. |
| `onDirtyChange` | `(dirty: boolean) => void`           | —       | Fired whenever the draft's dirty state changes. Wire this into a host's unsaved-changes / navigation guard (need not be memoized — the hook latches the latest callback). |
| `plugins`       | `FieldTypePlugin[]`                  | —       | The field-type registry available to insert, render, and validate against.  |
| `context`       | `FieldContext`                       | —       | Restricts which plugins the type picker offers (`plugin.availableIn`).       |
| `title`         | `ReactNode`                          | —       | Rendered on its own line **above the toolbar** — put a spec/content-type name here. Nothing renders when omitted. |
| `labels`        | `EditorLabels`                       | —       | Overrides for every author-facing string. Merges over `DEFAULT_EDITOR_LABELS`. |
| `formatSaveError` | `(reason: unknown) => string \| null` | —     | Formats a rejected `onCommit` reason into the `saveFailed` toast description; return `null` to suppress it. See [Save-failure description](#save-failure-description-formatsaveerror) below. |

### FieldKitProvider requirement

`SpecEditor` renders its live field previews through the same `FieldComponent`
the renderer uses (see [Config panel & live preview](#config-panel--live-preview)),
and that component calls `useFieldKit()` internally. **`SpecEditor` must
therefore be mounted inside the consumer's `FieldKitProvider`** — outside one,
it throws (`useFieldKit must be used within a FieldKitProvider`).

The provider is also how the config panel's type-settings editors reach the
adapters: a Fieldset's Blueprint picker lists through
`adapters.blueprint.list()`, degrading to Blueprint id entry where that
optional capability is missing.

The provider's `plugins` registry and the `plugins` prop passed to
`SpecEditor` must be **the same set**. They serve different jobs (the
provider resolves a field's component/adapters at render time; the `plugins`
prop drives the type picker, validation, and Zod generation), so a mismatch
between them is easy to introduce silently — e.g. a type offered by the type
picker but missing from the provider would insert a field the live preview
can't actually render, and vice versa.

## The Draft Model

`SpecEditor` never mutates `schema` directly and never calls `onCommit` on
every keystroke. Internally (`useSpecDraft`) it holds:

- **`baseline`** — the last schema this session knows to be committed. It
  starts as the `schema` prop and only ever moves forward on a
  **successful** `onCommit` resolution.
- **`draft`** — the live, in-progress schema every Build-mode edit applies
  to immediately (selection, insertion, drag, panel edits — all instant, all
  local).
- **`dirty`** — `draft !== baseline` (by reference; edits always produce a
  new array). Drives the header's `DirtyDot`, and enables/disables Save and
  Discard.

**Save** calls `onCommit(draft)` only when the draft is valid
(`spec.validation.valid`) and no save is already in flight. While the
Promise is pending, Save shows a loading state and both Save and Discard are
disabled. On resolve, `baseline` advances to the saved draft — `dirty`
becomes `false`. On rejection, `saveError` is set, an error toast
(`labels.saveFailed`) appears once per new failure, and — critically —
**the draft is left untouched and still dirty**, so the author can just fix
whatever failed and click Save again without losing anything.

**Discard** resets `draft` back to `baseline` and clears any `saveError`.

### The mid-flight-save semantic

Because `baseline` only advances on a resolved `onCommit`, a Discard that
happens *while a save is still in flight* does not cancel that save. If the
in-flight save goes on to succeed, `baseline` still advances to the schema
that was actually sent to the host — even though the visible `draft` was
already reverted. The practical effect: right after such a save resolves,
the editor can read as dirty again, because the (reverted) draft now
genuinely differs from what the host actually has stored. A further Discard
at that point restores the *actually-committed* content, not the
pre-in-flight-save content. This is deliberate: `dirty` always tells the
truth about draft-vs-server, never about draft-vs-"what the UI displayed a
moment ago."

### Schema-prop stability contract

`schema` is compared to `baseline` whenever the schema prop's reference
changes, by content — via an internal deep comparison that is
key-order-insensitive (`undefined`-valued keys are treated as absent; arrays
stay order-sensitive). This means a Postgres jsonb round-trip echo, which
reorders object keys on read-back, is content-equal to what was sent and
does **not** count as genuinely different content:

- **Same reference, or a new array with equal content** — ignored. This is
  the common case of a consumer re-rendering with a schema built fresh each
  time (e.g. from a `useState` or a query result) — it must not fight the
  author's in-progress edits or bounce `baseline` unnecessarily.
- **A new array with genuinely different content** — adopted as the new
  `baseline`. If the draft was clean, `draft` also snaps to it (this is how
  a background refetch or another editor updating the same spec propagates
  in). **If the draft was dirty, it is deliberately kept** — an author's
  unsaved work must survive an incoming prop change, even a legitimate one.
  In that case a warning toast (`labels.baselineConflict`) fires once, since
  the incoming content is no longer what the draft was based on — Save would
  now overwrite it. Applying a further edit, discarding, or saving all clear
  the notice.

The corollary hosts must respect: **update the `schema` prop only with
content you intend as a new baseline** — after `onCommit` resolves, or from
a genuine out-of-band change (e.g. another session's edit arriving over a
subscription). Passing a *stale*-content array (same identity purpose, older
data) after the fact will revert the baseline backwards for a clean draft.
Passing a fresh array with unchanged content on every render (normal React
hygiene) is always safe.

### Save-failure description (`formatSaveError`)

When `onCommit` rejects, the `saveFailed` toast now carries a description:
by default the rejection's `Error.message` (non-`Error` reasons are
stringified). Pass `formatSaveError={(reason) => string | null}` to
translate or sanitize the text; return `null` to suppress the description
entirely (the pre-0.7 title-only toast). The `saveFailed` label itself is
unchanged.

## The Toolbar

All editor chrome is ONE row (0.9.0, composition A2), left to right:

- **+ Card** and **+ Section** — outline buttons carrying the structural
  plugins' own icons (`PanelTop`, `LayoutDashboard`) beside their labels
  (`addCard`/`addSection`, defaults unchanged). "+ Card" appends an untitled
  card to the **active tab** (auto-wrap semantics unchanged — see
  [Cards](#cards)); "+ Section" appends a section and opens its inline
  rename input. Both are **disabled, never hidden**, in Preview mode — the
  bar keeps its shape across modes. "+ Card" is additionally disabled while
  the spec has no fields, with a tooltip (`labels.addCardDisabledEmpty`);
  "+ Section" works on an empty spec.
- **Dirty dot** — the unsaved-changes indicator (`labels.dirty`), beside
  the action cluster whose state it describes.
- **Build | Preview** — a segmented control (anker `SegmentedControl`; a
  radio group under the hood, so tests target `role="radio"`). The Preview
  segment is disabled while the draft has validation errors, with the
  `fixValidationFirst` tooltip. Switching semantics are unchanged: every
  entry into Preview mounts a fresh scratch form.
- **Discard** and **Save** (solid primary) — behavior unchanged.

The `title` prop renders on its own line above the bar; the bar itself
never contains it.

## Build Mode

### Selection & toolbar

Every shell carries an **always-visible drag grip** before its content —
the same header-grip treatment cards use — so reordering never requires
selecting first (0.10.0). Click (or focus + <kbd>Enter</kbd>/<kbd>Space</kbd>)
a field's shell to select it — a floating toolbar appears above the shell
(Edit, Duplicate, a cross-tab "Move to section" menu when the spec has 2+
tabs, and Delete; the grip lives on the shell, never in the toolbar), and
the [config panel](#config-panel--live-preview) opens to its right. System
fields (`field.system`) show an eye ("View definition") in place of Edit,
and Delete is hidden — see [System Fields](#system-fields).

### ⊕ insertion

A thin, hover-revealed (keyboard-focus-revealed too, for
<kbd>Tab</kbd>-only navigation) insertion row sits between every pair of
fields, before the first, and after the last in each tab. Clicking its ⊕
opens `TypePicker` in a popover, filtered by `context` and searchable; the
picked type is inserted at that exact position, auto-named and
auto-accessored (`nextAccessor`: `title`, `title_2`, `title_3`, …), and
immediately selected so the panel opens on it. An empty tab (or an empty
spec — the `Empty` story) shows its insertion row **always visible**, not
just on hover, plus a labeled empty-state message (`labels.emptySpec`).

### Sections & the section menu

Each tab's header carries a <kbd>⌄</kbd> menu: Rename (inline input, commits
on <kbd>Enter</kbd>/blur, cancels on <kbd>Escape</kbd>), Move left/right,
an orientation toggle (horizontal/vertical tabs — first section only, since
orientation is a whole-form setting), and Delete. **Deleting a section only
removes its marker field** — every field that belonged to it survives and
merges into the *previous* tab (or becomes the implicit first tab, if the
first section is deleted). The confirm dialog's message
(`labels.deleteSectionConfirm`) says so explicitly; nothing is destroyed.
"+ Section" (in the toolbar) appends a new section and immediately opens
its rename input.

### Cards

A tab's fields can be grouped into stacked, full-width **cards** — `card`
layout markers in the flat schema, one level below sections (fields after a
marker belong to that card until the next `card`/`section` marker). Cards
are purely visual: fields keep their top-level accessors and stored values
are byte-identical with or without markers.

**"+ Card"** (in the toolbar, next to "+ Section") appends an empty,
untitled card to the active tab. Adding the FIRST card to a tab that
already has loose fields
auto-wraps those fields into an untitled card first, then appends the new
card after it — a carded tab is always all-in-cards. The new card is
selected and the config panel's Name input focused so it can be titled
immediately. A card's title is optional (`config.name`): empty shows the
italic `cardUntitled` placeholder on the canvas and a plain, headerless
card in the rendered form.

Every card renders a **header bar**: a drag handle (moves the whole card —
marker plus contained fields — as one block; the canvas stays a single
flat sortable list, so dragging a *field* over another field reorders it
exactly as before, while dragging a field over a card's header FRAME snaps
it inside that card, at the top of its contents), the title, and a ⋯ menu.
Clicking the header selects the card; the config
panel then shows its one setting (Name) with the same live-edit semantics
as field renames. The ⋯ menu offers **Rename** (focuses the panel's Name
input), **Delete card** (removes only the marker — its fields merge into
the previous card; a first card's fields merge into the next; deleting the
only card returns the tab to the legal card-less state; nothing is
destroyed), **Delete card and fields** (destructive, behind the standard
confirm dialog), and — on a spec with 2+ tabs (0.12.0) — a **Move to
section** group listing every other section; picking one moves the whole
block there and follows it (see
[Drag & drop, including cross-tab](#drag--drop-including-cross-tab)).

Hand-written schemas violating the all-in-cards rule (a loose field
before a tab's first marker) are flagged by `validateSpec` as
`loose_field_in_carded_tab` on each loose field — those shells outline in
the danger color and Save/Preview disable — while the canvas and renderer
still degrade gracefully by framing them as an implicit untitled card.
The ⊕ insertion popover never offers the `card` type; "+ Card" is the only
way to add one (it owns the auto-wrap bookkeeping).

### Drag & drop, including cross-tab

Fields reorder within a tab via the shell's always-visible grip (pointer or
keyboard — see [Keyboard Support](#keyboard-support)). Since 0.11.0 the
canvas gives full mid-drag feedback (the drag-feedback rework):

- **A fixed-size preview follows the pointer** — a dnd-kit `DragOverlay`
  clone, portaled to `document.body`. Field drags carry a clone of the
  shell; card block-drags carry the card's HEADER BAR only plus a
  "+ N fields" count hint (`cardDragFields`/`cardDragFieldsOne`). The
  in-list original stays in place, dimmed with a dashed outline.
- **The list holds still**: no other shell or frame moves, scales, or
  reflows during a drag. (Pre-0.11, dnd-kit's list strategy scaled the
  dragged node to the hovered slot's size and translated nested card
  frames independently of their children — both artifacts are structurally
  gone.)
- **A 3px accent insertion line with an end-dot marks the exact drop
  slot** — between shells, between card frames (block drags), at a card's
  top, or inside an empty card — and **the card that would receive the
  field washes with a soft accent background tint** (background only; the
  accent *border* remains the selection channel; card block-drags tint
  nothing). Line, tint, and the executed drop all derive from ONE
  resolution (`resolveDropTarget`), so the preview can never disagree with
  the result.
- Dragging a field or card block's row onto another tab's *trigger*
  **highlights the trigger** immediately (no line) but — since 0.12.0 —
  does not switch the view on first contact. **Spring-loaded sections**:
  resting the pointer on the trigger for a dwell (`SPRING_DWELL_MS`,
  500 ms) springs the canvas to that tab while the drag continues, so the
  existing insertion line / card tint can guide the drop to an exact slot
  inside the now-visible foreign section. Springs chain — hovering a
  further trigger later in the same drag springs again. Crossing the tab
  strip in well under the dwell never flips the view.
- **Keyboard drags skip the dwell**: landing on a trigger's drop zone
  switches the visible tab **immediately** — an arrow-key landing is
  already a deliberate action, unlike a pointer passing through. Further
  arrows walk the sprung tab's slots for exact placement; the overlay
  glides to each announced slot with the same line, tint, and trigger
  highlight as a same-tab keyboard drag.
- **Releasing on a trigger before the dwell elapses** (a "quick drop")
  keeps the pre-spring semantics: the item appends to the **end** of that
  section — a field lands inside the tab's last card when the tab is
  carded; a card block appends after the tab's last element — without the
  canvas ever visibly springing.
- **Every cross-section drop — sprung or quick — ends on the target tab**:
  the canvas switches `activeTabIndex` there, selects the moved field or
  card, and scrolls its shell (or card header) into view. Same-tab drops
  are unaffected (no follow, no reselect) — this is the same follow
  behavior the toolbar's per-field "Move to section" menu and the card ⋯
  menu's own move group ([above](#cards)) now perform too. Dropping onto a
  field's or card's own current tab trigger is a no-op and shows no
  highlight (the hover still springs/switches the view).
- **Escape, and any drop that resolves to nothing** (including releasing
  back onto the drag's own tab trigger), restore the tab that was active
  when the drag *started* — a spring is only a preview until a drop
  commits.
- **Card blocks can now cross sections**, both by drag (spring to a
  foreign tab, then drop between its frames or onto its trigger for a
  quick end-append) and via the card ⋯ menu, which gains a
  "Move to section" group beneath Rename / Delete card / Delete card and
  fields, listing every *other* section; picking one moves the whole
  block and follows it exactly like a field's cross-tab move. The group's
  caption reuses the existing `moveToSection` label — no new label key —
  and the group is omitted entirely on a single-tab spec (nothing to move
  to). A card arriving in an UNCARDED section auto-wraps that section's
  loose fields into an untitled card first (0.13.0, mirroring "+ Card"'s
  idiom) — the editor's own moves never violate the all-in-cards rule.

### Field search

A search box (mirroring `SpecForm`'s, `/` to focus, accessible name
`labels.searchLabel`) filters across every tab by name or accessor. Unlike
the renderer's read-time search, the editor's index **includes hidden
fields** (`config.hidden`) — they're real, selectable rows in Build mode
(rendered as an italic "Hidden field: {name}" placeholder instead of their
live input), since an author must be able to find and edit them even though
end users in Preview/production never see them.

### Delete-undo toast

Deleting a field doesn't ask for confirmation up front — it removes the
field immediately and shows a toast (`labels.fieldDeleted`) with an
**Undo** action that re-inserts it at its original flat position. Undo
reads the *live* draft at click time, not a snapshot from when the toast
appeared, so it stays correct even if you kept editing (or deleted more
fields) before clicking it. It's a single-level, best-effort undo — the
insertion index clamps rather than throws if the schema's shape changed
enough to make the original position ambiguous.

### Validation surfacing

Every draft change re-runs `validateSpec`. A field with an error (currently:
duplicate accessor, empty name, empty accessor) gets a danger-colored shell
outline; any tab containing an errored field shows a numeric badge on its
trigger counting that tab's errors. **Save and the Preview segment are both
disabled** while `validation.valid` is `false` — Preview's disabled state
carries a tooltip (`labels.fixValidationFirst`) explaining why. See the `InvalidDraft`
story below.

### Config panel & live preview

Selecting a field opens a fixed-width right-hand panel with three **tabs**
(0.10.0 — previously collapsible sections): **General** (name, accessor,
instructions, required, default value, hidden/read-only/localizable, and —
`group` fields only — a read-only Children list with per-row Edit buttons
that drill the panel into a child, with a Back control), **Validation**
(min/max length, pattern + message, unique), and **Type settings** (the
plugin's own settings UI). Panel order, top to bottom: Back row (drill-in
only) → header (name/type/close) → duplicate-accessor banner (above the
strip — visible from ANY tab) → tab strip → tab body. The active tab is
panel-local state: General is the default, and the panel RESETS to General
whenever the selected field changes, drill-in frame changes included. All
three tab bodies stay mounted (hidden, not unmounted), so an in-progress
accessor edit survives a tab switch. System fields short-circuit BEFORE the
tab strip (the read-only summary replaces the tabs entirely); cards render
their single Name body with no tab strip. The canvas
re-renders the field's real component live as you edit its config, via the
same `FieldComponent` the renderer uses, wired to a scratch
`react-hook-form` instance seeded with the spec's own default values — so
what you see in Build mode is a faithful preview, not a mock. `group`
fields render a framed name+count preview instead (their real component
needs a populated `useFieldArray`, which reads as broken with zero items on
an inert canvas).

Canvas previews also follow the same §10 required/optional marker
convention the rendered form will use, derived **live** from the draft
(`resolveMarkerConvention`): toggling a field's Required checkbox in the
panel can flip every preview's markers — asterisks on the required fields
versus a muted `(optional)` after the optional ones — the instant the
majority changes, without leaving Build mode. Preview mode applies the
identical convention through the real `SpecForm`, so both modes render
markers exactly as the finished form will.

The accessor input has its own local, possibly-invalid state: editing the
**name** auto-derives the accessor via slugify *until* the accessor has
been manually edited once (an "auto-slug latch") — and that latch starts
**already engaged** for any field whose accessor was already committed
(present in the last-saved `schema`), so a simple rename can never silently
re-slug and disconnect a saved field's data. Manually typing an accessor
that collides with a sibling, or is empty, shows an inline error and is
**not** applied to the draft until fixed. Changing the accessor of an
already-committed field (even validly) shows a non-blocking warning
(`labels.committedAccessorWarning`) — the data stored under the old
accessor won't follow.

## System Fields

Fields with `system: true` are host-owned definitions (typically injected
server-side and re-canonicalized on every read). The editor treats them as
locked content:

- The config panel renders a **read-only summary** (`panelSystemNotice` +
  accessor/required/instructions) instead of the editable sections — nothing
  interactive is mounted, including the plugin's `settingsComponent`.
- The shell toolbar shows an **Eye** ("View definition") in place of Edit,
  and hides **Delete**; the shell's always-visible grip stays enabled —
  authors arrange system fields freely among their own. Clicking the eye
  opens the same read-only definition summary as clicking the shell itself
  (`onSelect`, not `onEdit` — there is nothing to focus in a read-only
  panel).
- **Duplicate** produces a copy with `system: false` — a copy is always
  user-owned.

The editor never *creates* system fields; they arrive via the `schema` prop.
Hosts are responsible for re-canonicalizing system definitions on read so a
stored spec can never drift from the application's truth.

## Preview Mode

Selecting **Preview** in the toolbar's mode control (disabled when the
draft is invalid) mounts the draft
schema as a real, independent form — its own `react-hook-form` instance and
Zod resolver, sharing nothing with Build mode's scratch preview form or with
any host form. Submitting shows a success toast (`labels.testSubmitSuccess`);
nothing is persisted anywhere. **Every entry into Preview force-remounts the
view** (via a bump counter), so scratch data typed in a previous visit can
never leak into or survive a later one. Selecting **Build** returns to
editing without losing the draft.

### Fieldset resolution

Preview is a consumer of the draft like any other, so it runs the two-phase
load ADR-0004 requires: `resolveSpec(draft, adapters)` first, then the Zod
schema built from the **resolved** draft. That is what makes a required field
inside a Fieldset block the test submit — unresolved, a Fieldset validates as
an opaque record, and Preview would pass a form the real one rejects.

The adapters come from your `FieldKitProvider` (see
[FieldKitProvider requirement](#fieldkitprovider-requirement)); nothing new is
passed to `SpecEditor`. Behavior by case:

- **Blueprint adapter configured** — Preview shows a spec-shaped skeleton
  while the Blueprints load, then the real form with the embedded fields
  validating as their own.
- **No blueprint adapter** — nothing can be fetched, so nothing is awaited:
  Preview renders immediately and each Fieldset shows its
  "Blueprint adapter not configured" stub. Same for a draft with no Fieldset
  in it — no skeleton frame it never needed.
- **Resolution failed** — a `labels.previewResolveFailed` warning alert sits
  above the form, the unresolved draft renders below it (Fieldsets degrade to
  their own "Failed to load blueprint fields" state), and the editor is
  otherwise untouched: **Build** still returns you to the canvas.

Resolution follows the **draft**, re-running whenever it changes — Preview
never shows the last saved spec.

## Keyboard Support

- **Shells**: focusable (`tabIndex=0`); <kbd>Enter</kbd> or <kbd>Space</kbd>
  selects, matching click.
- **Reordering**: the shell grip (always visible — no selection needed) is
  a `dnd-kit` `KeyboardSensor` target —
  focus it and press <kbd>Space</kbd> to lift, <kbd>↑</kbd>/<kbd>↓</kbd> to
  move, <kbd>Space</kbd> again to drop, <kbd>Escape</kbd> to cancel. Since
  0.11.0 keyboard drags render the identical feedback to pointer drags:
  the overlay preview glides to each announced slot, and the insertion
  line, card tint, and tab-trigger highlight track every move.
- **Insertion**: the ⊕ trigger becomes visible on keyboard focus (not just
  hover), satisfying WCAG 2.4.7 — you never Tab onto an invisible control.
- **Section menu / rename**: standard menu keyboard nav
  (<kbd>Home</kbd>/<kbd>End</kbd>/arrows/<kbd>Enter</kbd>); the rename input
  commits on <kbd>Enter</kbd> and cancels on <kbd>Escape</kbd> without
  bubbling to the shell-deselect handler below.
- **Escape (Build mode, global)**: clears the current field selection —
  unless something with its own Escape handling (an open menu, popover, or
  the rename input) already consumed the event.

## Migration to 0.12.0

Adds spring-loaded cross-section drag (see
[Drag & drop, including cross-tab](#drag--drop-including-cross-tab) above) —
**no API changes, no new label keys**. The card ⋯ menu's new "Move to
section" group reuses the existing `moveToSection` label as its caption.

- The 0.8.0 guard that confined a card block's drag to its own tab is
  retired: a card can now cross sections by drag (after a spring) or via
  the ⋯ menu. Accidental moves remain impossible — a hidden tab's
  droppables stay filtered out of collision detection regardless, so a
  card can only land in a section the author has actually made visible
  (by spring, or by having already switched tabs).
- **Behavior change hosts may notice:** hovering a foreign tab's trigger
  while dragging used to switch the visible tab **instantly**. It now
  requires a ~500 ms dwell first (crossing the tab strip no longer flips
  the view by accident); releasing before the dwell elapses still appends
  to that section immediately, unchanged from before. Keyboard drags are
  unaffected — landing on a trigger's zone still switches instantly.
- **Behavior change hosts may notice:** the toolbar's per-field "Move to
  section" menu previously left the author on the source tab after the
  move. It now follows the moved field to its new tab, selects it, and
  scrolls it into view — the same follow behavior cross-tab drag drops and
  the new card move menu perform.

## Migration to 0.11.0

Visual-only rework of mid-drag feedback — **no API changes, no
drop-semantics changes** (every drop lands exactly where it did in 0.10):

- Dragging now shows a **fixed-size overlay preview** (a dnd-kit
  `DragOverlay`, portaled to `document.body`) instead of transforming the
  real shell; the origin stays in place, dimmed (opacity 0.35, dashed
  outline, `data-drag-origin`). The pre-0.11 scale artifact (a dragged
  shell stretching to the hovered slot's size) and frame escape (a card's
  child floating outside its frame) are gone at the root.
- **No list reflow during a drag**: other shells/frames no longer
  translate out of the way. The insertion point is announced by a 3px
  accent line with an end-dot (`data-testid="drop-indicator"`, slot
  identity in `data-position`), plus a soft background tint on the
  receiving card and a highlight on a hovered foreign tab trigger (both
  `data-drop-target="true"`).
- Two new label keys caption the card block-drag preview's count hint:
  `cardDragFields` (`"+ {count} fields"`) and `cardDragFieldsOne`
  (`"+ 1 field"`).
- Tests that asserted dnd-kit transforms on shells mid-drag
  (`translate3d`/`scaleY` inline styles) should assert the new feedback
  surfaces instead. jsdom keyboard-drag tests that mock
  `getBoundingClientRect` must give `[data-testid="drag-overlay-preview"]`
  the dragged item's initial rect — dnd-kit derives the keyboard collision
  rect from the overlay once it mounts (see `docs/dnd-kit-reference.md`).

## Migration to 0.10.0

Visual-only rework — **no API changes**:

- The config panel's collapsible General/Validation/Type-settings sections
  became **tabs** (anker Tabs: `role="tab"` / `role="tabpanel"`). Tests that
  clicked the old `panel-toggle-*` disclosure buttons should click the tabs
  instead. Three new label keys caption them — `panelTabGeneral`,
  `panelTabValidation`, `panelTabType` — while the old `panelGeneral`/
  `panelValidation`/`panelTypeSettings` keys still exist (keys are frozen)
  but are no longer rendered anywhere.
- **Keyboard Tab order through a SELECTED shell changed:** the drag grip
  used to be the selection toolbar's first button; it is now a standalone
  always-visible control that follows the toolbar in DOM order, so Tab
  visits Edit → Duplicate → Move → Delete → grip (previously grip-first).
  Unselected shells are unaffected (the grip is their only control).
- All three tab bodies stay **mounted** (inactive ones `hidden`): a
  plugin's `settingsComponent` now mounts as soon as its field is selected,
  not when the Type-settings section is first expanded.
- The panel has a **fixed width** — it previously grew with its widest
  section's content, so system/custom/card selections rendered different
  panel sizes.
- The drag handle is **always visible** on every shell (the card-header
  grip idiom) and the selection toolbar no longer contains one. Keyboard
  drag, Escape-cancel, and system-field drag+lock behavior are unchanged.
  Tests that selected a field to reach the `labels.dragField` handle should
  instead query the grip inside the shell (it is no longer unique
  page-wide).

## Migration from 0.1

`SpecEditor`'s 0.1 API (`onChange: (schema: Schema) => void`, firing on
every edit) is replaced by the draft session described above:

1. Rename the prop: `onChange` → `onCommit`. It now fires **once**, only on
   Save, not on every keystroke.
2. **Remove any per-edit persistence** your host was doing in `onChange` —
   there is no equivalent hook for "an edit just happened locally"; the
   whole point of the draft model is that nothing reaches the host until
   Save.
3. If your host needs leave-protection (an unsaved-changes guard, a
   route-change confirmation), wire the new `onDirtyChange` prop into it
   directly — it fires exactly when `SpecEditor`'s internal dirty state
   changes.
4. If your `onChange` handler ever awaited a request, return that same
   Promise from `onCommit` instead — `SpecEditor` now natively handles the
   pending/rejected states (loading Save button, error toast, draft stays
   dirty) that you previously had to build yourself.
5. Review the [schema-prop stability contract](#schema-prop-stability-contract)
   above — if your host previously fed `schema` from the same state
   `onChange` wrote to on every keystroke, that pattern no longer applies;
   `schema` should now reflect only the committed content.
6. Confirm your host renders `SpecEditor` inside its `FieldKitProvider`, and
   that the provider's `plugins` and the `plugins` prop you pass to
   `SpecEditor` are the same set — see the
   [FieldKitProvider requirement](#fieldkitprovider-requirement) above.
7. **`FieldModal` and `FieldModalProps` were removed from
   `@knkcs/fieldkit/editor`'s public exports in 0.2.0** — field
   configuration is now the built-in side panel described in
   [Config panel & live preview](#config-panel--live-preview), opened by
   selecting a field on `SpecEditor`'s canvas. There is no standalone
   drop-in replacement exported for a "configure one field outside
   `SpecEditor`" use case; remove any direct `FieldModal`/`FieldModalProps`
   imports — they will fail to resolve.

## Known Limitations

- **Group children have no add/remove UI.** The General tab's Children list
  (drill-in only) lets you *edit* an existing child field's config, but
  there is no in-editor way to add or remove a group's children — author
  those via `defineSpec()` / hand-authored `Field[]` up front.
- **No condition-editing UI.** `FieldCondition` exists on the schema type,
  but the renderer doesn't evaluate conditions yet, so an authoring UI for
  them is deferred until that lands.
- **Toasts.** SpecEditor mounts anker's `<Toaster />` for its own toasts
  (save errors, delete-undo, Preview submit). Hosts that mount a global
  `<Toaster />` are fine on anker ≥ 3.1.1, which dedupes mounted regions
  (each toast renders once); on anker 3.1.0 both regions render and
  toasts appear twice while the editor is mounted.
