# Section

A structural divider that splits a specification into tabs. **Rendering the tabs is [SpecForm](?path=/docs/renderer-specform--docs)'s job, not `FieldRenderer`'s** — this field type's own `fieldComponent` returns `null` and produces no visual output by itself.

## When to Use

Insert a `section` field wherever a new tab should start. Fields before the first `section` field land on an implicit first tab (labeled `"General"` by default); every `section` field after that opens a new tab named after it. If a schema has no `section` fields at all, `SpecForm` renders it flat with no tab strip.

`FieldRenderer` itself does not special-case `section` fields — passing a schema with sections directly to `FieldRenderer` (bypassing `SpecForm`) renders every field in a flat list with no visible divider, since the section's `fieldComponent` returns `null`. Use `SpecForm` when a schema may contain sections.

## Settings

| Setting       | Type                         | Default        | Description                                                                 |
|---------------|------------------------------|----------------|-------------------------------------------------------------------------------|
| `orientation` | `"horizontal" \| "vertical"` | `"horizontal"` | Whole-form tab orientation. Only the **first** section's value is read; later sections cannot override it. `SpecForm` auto-degrades `vertical` to `horizontal` below ~560px container width. |

## Validation

The Zod schema returns `z.never()` — section fields should never appear in form data.

## Zod Output

```ts
z.never()
```

## Table Cell

No cell component — section fields are not data-bearing.

## Known Limitations

- The `fieldComponent` returns `null` — the field itself renders nothing; the tab UI comes entirely from `SpecForm`, so a schema with sections rendered through bare `FieldRenderer` shows no divider and no tabs.
- Zod schema uses `z.never()` which may cause issues if the accessor appears in form data.
