# Reference

A **Reference Tree**: References to other Contents, ordered and nested. Each row shows the referenced Content's *current* name, resolved through the `reference` adapter; adding one opens a drawer that browses the catalogue. Requires a `reference` adapter configured via `FieldKitProvider`.

## When to Use

Use **Reference** when a field holds several links to other Contents — "Related articles", "Cited works", "Featured items" — and when the arrangement of those links is itself meaningful. For exactly one Reference, use [Single Reference](?path=/docs/fields-single-reference--docs), which is a separate field type because the two store incompatible values (ADR-0005).

Each Reference can also carry **Attributes** — values about the pointing itself rather than about either Content, such as the page a citation appears on. See [Attributes](#attributes).

## The Tree

Every row carries a drag grip. Dragging a row reorders it among its siblings; dragging it rightwards nests it under the Reference above, one level per `24px` of travel. **A Reference's descendants travel with it** — a branch keeps its shape however far it moves.

A Reference with children carries a chevron that folds its branch away, so one branch can be worked on without the rest in the way. A tree of more than `REFERENCE_TREE_COLLAPSE_THRESHOLD` References **opens with every parent collapsed**; at or below it, expanded. The threshold is a provisional guess and wants tuning against a real Spec. Folding is the control's own state and is never stored.

Folding and dragging agree on two rules. A folded Reference **stands in for its whole branch**: dropping below one lands below everything it hides, and a drop can reach a depth of "child of the folded Reference" but never deeper — a drop may only land somewhere an Author can see. And whatever a Reference lands *inside* is **unfolded on the drop**, so it is visible where it went.

Dragging works from the keyboard as well as the pointer: focus a grip, press <kbd>Space</kbd> to lift, <kbd>↑</kbd>/<kbd>↓</kbd> to move between rows, <kbd>←</kbd>/<kbd>→</kbd> to change how deeply the drop nests, then <kbd>Space</kbd> to drop or <kbd>Esc</kbd> to cancel.

The depth a drop lands at is decided by **pure functions** in `src/schema/reference-tree.ts` — read the stored value, flatten, project a depth, move the branch, re-nest, write back — so none of the drag arithmetic is asserted through a DOM.

There is no pagination, deliberately: it cannot coexist with dragging to a position nobody can see.

## Value

Fieldkit owns the shape; a Consumer maps it to whatever it persists (ADR-0008).

```ts
// The stored value
Reference[]

interface Reference {
  id: string                            // the referenced Content
  pin?: string | null                   // the Pin's target id; absent = newest Version
  attributes?: Record<string, unknown>  // keyed by the Attribute's accessor
  children?: Reference[]                // the branch under this Reference
}
```

The nesting is genuine rather than a flat list with ancestor ids, which is what makes an orphan unrepresentable. Flat encodings are the Consumer's business.

Form data is only as well-formed as whatever produced it, so a stored entry that is not a Reference renders no row. Removing and dragging both leave such an entry at the top-level position it held; one nested inside a branch does not survive a drop, because every branch is rebuilt from depths — and a value holding one cannot pass the Schema anyway.

A display name is **never stored**. Names are resolved through the adapter on every load, so a Content renamed elsewhere reads correctly here, and one that no longer resolves keeps its id on screen rather than vanishing.

`pin` holds **only the target id**. Which *kind* of target it is comes from the field's `pin_mode`, never from the value (ADR-0008) — which is why changing `pin_mode` invalidates every stored pin at once rather than leaving some stale. No pin at all means the Content's newest Version.

## Settings

| Setting      | Type                               | Default  | Description                                                        |
|--------------|------------------------------------|----------|--------------------------------------------------------------------|
| `blueprints` | `string[]`                         | `[]`     | The blueprints this field may point at. Empty means the adapter decides |
| `max_items`  | `number`                           | —        | At most this many References, counted over the whole tree — a nested child counts as much as a root |
| `max_depth`  | `number`                           | —        | How many **levels** the tree may hold, roots being level 1. `1` is a flat list; `2` allows one level of nesting |
| `pin_mode`   | `"none" \| "release" \| "version"` | `"none"` | Whether References are fixed to a release, to a version, or track the newest version. Absent reads as `"none"` |
| `attributes` | `Field[]`                          | `[]`     | The Attribute Spec — the Fields every Reference carries about the pointing. See [Attributes](#attributes) |

`max_depth` is a **count of levels, not the index of the deepest one** — the dialect every other `max_*` setting in this package speaks, and the one knkCMS core's `reference` speaks too. The tree model works in 0-based depth indices, so the conversion happens once, in `referenceDepthCeiling()`; `referenceItemCap()` is its twin for `max_items`. Read both through those functions rather than with `?? 0`: **an unset cap is no cap**, and `0` is a cap of zero. Conflating the two is how an uncapped field ends up refusing to add anything.

The Blueprints control is the shared `BlueprintPicker`, so it falls back to blueprint-id entry when the blueprint adapter cannot enumerate blueprints. Each cap is a number box whose empty state means "no limit" — emptying it removes the key rather than storing `0`. `pin_mode` is a select, with a warning that changing it strands every pin already saved — fieldkit cannot refuse the change, because only a Consumer knows whether any Content would be stranded (ADR-0008); a Consumer freezes the setting through `config.locked_settings` instead.

## Attributes

An **Attribute** is a value a Reference carries about the *pointing* — the page a citation appears on, the role a credit names — not about either Content. An Author declares them once per field, as a Spec of ordinary Fields, so "page" can be a number and "role" a select and either can be required. Someone filling in the form opens a drawer per Reference and fills them in with real controls.

Values are stored **keyed by Accessor** on the Reference itself, which is what makes them survive: moving a Reference moves its whole entry, Attributes included, so nothing has to keep a parallel structure in step. In knkCMS core these are bare strings positionally aligned to a settings array.

Each row shows a **filled count** — `1/2` — so it is visible at a glance which References still need attention. The count is over exactly what the Schema composes: a hidden Attribute, a value-less Marker a hand-written Spec slipped in, and an entry that is not a Field at all are none of them counted, asked for, or composed — a stray costs itself and nothing else. A key left behind by an Attribute since deleted is not counted either. `false` and `0` count as filled: they are what an unchecked box and a zero page number are, and the count must not disagree with the Schema about whether a required Attribute is satisfied. A field declaring no Attributes shows no affordance at all.

### Authoring them

The Attribute Spec is authored in the config panel's **Type settings** tab. Adding one is the ordinary type picker; configuring one is the panel's incumbent **drill-in** — the same Back control, the same three tabs, the same accessor gate a group's child gets. There is no separate nested editor.

The picker offers strictly less than the canvas does, through a new `FieldContext` value, `"attribute"`:

- **no Markers** — a drawer has no Tab and no Card for a Section or a Card to open;
- **no containers** — `group`, `fieldset` and `blocks` would be composed but never checked (see the boundary below);
- **no reference types** — cycle rejection walks `children`, so a Reference Field declared as an Attribute is a recursion nothing would catch.

### The settings-nested boundary (ADR-0007)

The Attribute Spec lives in `settings.attributes`, following the Blocks precedent, and inherits ADR-0007's boundary **verbatim**. `resolveSpec()`, `validateSpec()` and `resolveMarkerConvention()` walk `Field.children` only, so nothing shared reaches an Attribute Field. Concretely:

- a **duplicate accessor** between two Attributes is never reported — the later one silently wins the composed shape (the editor generates unique accessors, so only a hand-written Spec can produce one);
- an **empty name** and an **empty accessor** are never reported either;
- a **Fieldset** declared as an Attribute is never resolved, and composes as the opaque record any unresolved Fieldset does — which is why the picker does not offer one.

The reference plugin composes the Spec itself, exactly as the Blocks plugin composes a block type's fields. Composing is not walking, so the boundary is unmoved. `src/schema/reference-attributes.ts` is where this is written down.

## Pinning, and the drawer's second step

When `pin_mode` is `"none"` the add drawer has **exactly one step**: picking a Content stores `{ id }` and closes, and the adapter is never asked about pin targets.

When the field pins, picking a Content opens a **second step** listing what that Content may be pinned to. Choosing a target stores `{ id, pin }`; choosing **Newest version** — always first, and available even while the targets load or after a lookup that failed — stores `{ id }` with no `pin` key at all. **Back** returns to the browse, still narrowed to whatever was searched, having stored nothing.

## Adapter Interface

```ts
reference: {
  search: (query: ReferenceSearchQuery) => Promise<ReferenceSearchResult>;
  fetch: (ids: string[]) => Promise<ReferenceItem[]>;
  listPinTargets?: (              // optional
    contentId: string,
    mode: "release" | "version",
  ) => Promise<PinTarget[]>;
  getSearchFilters?: () => Field[];   // optional
  getResultColumns?: () => Field[];   // optional
}

interface PinTarget {
  id: string;            // what `pin` stores
  label: string;         // what the person reads
  description?: string;  // a second line, where one helps
}

interface ReferenceSearchQuery {
  blueprintIds: string[];
  query: string;
  filters: Record<string, unknown>;   // opaque to fieldkit
  excludeIds?: string[];              // optional — already referenced
  page: number;                       // 1-based
  page_size: number;
}

interface ReferenceSearchResult {
  items: ReferenceItem[];
  total: number;                      // across every page
}
```

`search` is a query object rather than positional arguments because a browsable picker over a real catalogue needs pagination and a total, which the old bare-array signature could not express (ADR-0009).

### The adapter describes itself with Specs

Filtering and columns mean domain nouns — a status, an assigned user — that fieldkit's catalogue must not learn. So the adapter describes them instead: `getSearchFilters()` returns the `Field[]` describing a query, `getResultColumns()` returns the `Field[]` describing one Content row. Fieldkit renders the first with `FieldRenderer` and the second with `SpecDataTable`, so each field type brings its own control and its own cell for free.

The values the filter form collects travel back through `search` as `filters` — **an opaque record fieldkit never inspects**. A filter no field type can express needs a new field type rather than a bespoke control.

Both methods are **optional**. Without them the picker degrades to a search box and a name column, which is what a Consumer that has not implemented them should get rather than an error.

### Contents already in the tree

The picker does not offer a Content the field already holds — adding it again would put the same Content in the tree twice. The ids travel with the search as `excludeIds`: **every Reference at every level**, not just the roots, deduplicated, and read from the same flattening `max_items` counts.

The field is **optional and additive**, on the same terms as the methods above. An adapter that honours it excludes them at the source, so its `total` counts exactly what it returned. An adapter that ignores it is not wrong, only less precise: fieldkit drops them from the page it was handed either way, so the picker still offers none of them — but the total is the adapter's, so it still counts the Contents nobody can pick. A Consumer written before the field existed keeps working unchanged.

This is a **policy about the picker, not about the value**. A Reference Tree keys its rows by path precisely so the same Content *can* appear twice; nothing here refuses such a value, rewrites one, or stops a drag producing one. [Single Reference](?path=/docs/fields-single-reference--docs) applies the one-item version of the same rule.

`listPinTargets` is **optional on the same terms**. Only the adapter knows a Content's Releases or Versions, and it is the adapter that normalises whichever kind was asked for into an id, a label and a description — so **fieldkit models neither a Release nor a Version**. Without the method a pinning field offers the newest Version and nothing else: the same answer a Consumer gets from returning an empty list, and the same one the field already shows while the targets are in flight. A Consumer that has not implemented pinning gets that rather than an error.

The absence is **silent** — it is a configuration, not a failure — where a call that *rejects* is reported through the provider's `onError`. It is called only when the field pins, and only once a Content is chosen.

## Validation

| Rule        | Description                                              |
|-------------|----------------------------------------------------------|
| `required`  | At least one Reference                                    |
| per item    | Each entry must be a Reference — an object with a non-empty `id` |
| per branch  | A nested Reference is held to the same rules as a root one |
| per Attribute | Each declared Attribute is checked as the type it is; a required one blocks submit and reports at its own key under the Reference that owns it |
| `max_items` | The flattened tree holds at most that many References. Reported **at the field's path** |
| `max_depth` | No Reference sits deeper than that many levels. Reported **at the offending Reference's path** — `related.0.children.1` |

```ts
// Optional
z.array(referenceTreeSchemaWith(attributes)).superRefine(caps)

// Required
z.array(referenceTreeSchemaWith(attributes))
  .min(1, "Related articles is required")
  .superRefine(caps)
```

The node schema is **lazily recursive**: it names `children`, so a nested branch survives a parse. An object schema that did not would strip the branch, and a drop that nested a Reference on screen would submit a flat list. The recursion is also what puts the Attribute Spec on every Reference at every level.

`attributes` is the Attribute Spec composed through the plugin's `composeChildren` argument (ADR-0007), and takes one of three shapes:

- **no Attribute declared** — the opaque `Record<string, unknown>` ADR-0008 declares, unchanged from before Attributes existed;
- **no required Attribute** — the composed object, optional and `passthrough`, so a Reference carrying nothing stores no `attributes` key at all;
- **a required Attribute** — the same object with a `{}` default, so a Reference added before the Attribute was declared cannot slip past the check.

`passthrough` throughout, as both container types do: a stored record carries keys the Spec no longer declares, and validation arriving is no reason to prune an Author's data. A required Attribute reports at `related.0.attributes.role` — under the Reference that is missing it — and at `related.0.children.0.attributes.role` for a nested one.

The blast radius mirrors ADR-0007's: declaring a required Attribute starts checking every stored Reference of that field, so data that saved successfully before can begin blocking submit.

Both caps live in the **Schema**, not only in the control, so an import or an API write is checked on the same terms a form is. The UI additionally disables the add affordance at `max_items` and clamps a drop to `max_depth`, but neither is where the rule lives.

That has a blast radius, and it is intended: **a Spec whose caps were never enforced can begin blocking submit on data that saved fine before.** What does not happen is fieldkit quietly fixing it — a value over a cap is reported, never truncated, and a branch past the depth is reported, never re-nested. Only the shallowest Reference in each over-deep branch is reported, since everything under it is too deep because of it.

`ReferenceField` renders those messages under the tree, because `FormField` shows only the message on the field's *own* node and `max_depth` deliberately reports deeper. The same collection catches a required Attribute, which reports at `related.0.attributes.page` for the same reason — and which lives inside a drawer, so without it a submit blocked by an Attribute would be a submit blocked by nothing visible at all.

## Table Cell and Read Mode

`ReferenceCell` renders a count — "3 references" — at table density, counting **every** Reference at every level, exactly as `max_items` does. Not the names: a cell has neither adapter access nor async, so the alternative is a row of raw ids. `SingleReferenceCell` counts on the same terms ("1 reference"), so the two types read alike in one table.

Read mode bypasses the cell and renders the tree instead: `ReferenceReadValue` resolves every Content's current name through the adapter, indents each Reference to its depth, and shows each Reference's Attribute values against it. It sits inside the renderer, so it reaches the adapter and has the height a table row does not (ADR-0008). It never folds — collapsing is there to make a tall tree draggable, and there is nothing to drag when reading — and it never touches react-hook-form, so read mode still needs no `FormProvider`.

The bypass is the plugin's own `readComponent` rather than a `field_type` branch in read mode's code (ADR-0007). For reference types that is not merely tidier but necessary: a minted type carries its own id, which no list of names in shared code could contain, so `toc_reference` gets the same read mode `reference` does.

## Minting a reference-shaped type of your own

The catalogue stays generic, but it exports the parts (ADR-0010). A field type whose meaning is *your* domain — a table-of-contents reference, a publication tree — is a `createReferencePlugin()` call rather than a rebuilt tree:

```ts
import { createReferencePlugin } from "@knkcs/fieldkit/schema";
import { BookOpen } from "lucide-react";

export const tocReference = createReferencePlugin({
  id: "toc_reference",              // what a Spec stores, and what a backend addresses
  name: "TOC Reference",
  description: "The publication tree this Content hangs in",
  icon: BookOpen,
  maxPerSpec: 1,                    // one per blueprint
  availableIn: ["blueprint"],
});
```

Pass it to `FieldKitProvider` and `TypePicker` beside `builtInFieldTypes` and it behaves as a built-in does: the same tree, the same browse drawer, the same count cell, the same read mode, the same settings editor, the same Schema. Only the catalogue entry is yours — `id`, `name`, `description`, `icon`, `category`, `maxPerSpec`, `availableIn`, and `defaultSettings`, which is merged **over** the reference defaults so naming blueprints does not silently turn pinning on.

`maxPerSpec` is enforced everywhere it always was: `validateSpec()` reports a second instance, the type picker greys the type out once one exists, the canvas blocks the duplicate, and `SpecEditor` refuses to save.

**Registering a replacement is not a migration.** Fieldkit's removed `toc_reference` stored a bare id string; a minted type stores a Reference Tree, so stored values have to be converted — `"x"` becomes `[{ id: "x" }]` — or they fail the Schema and render as an empty tree. Its `always_latest` and `attributes` settings keys are gone with it; `pin_mode: "none"` is what `always_latest` meant.

For a control of your own around the same tree, `ReferenceTree` is exported from `@knkcs/fieldkit/renderer`. It is the rows and the dragging, not the Field: it takes `rows` (from `readReferenceTree(value)`), the stored `value`, an `onChange` that receives the whole next value, `names` — a record keyed by Content id — and `depthCeiling`, a 0-based depth index that `referenceDepthCeiling(settings)` converts a `max_depth` setting into. Resolving those names, and offering any way to *add* a Reference, stay yours, because only your Adapter can do either. `readReferenceTree`, `countReferences` (every Reference at every level, what `max_items` caps), `referencesPastDepth` (where a tree breaks `max_depth`), `referenceItemCap` and `referenceDepthCeiling` all come from `@knkcs/fieldkit/schema`.

## Errors

An adapter failure reaches the Consumer's `onError` on `FieldKitProvider`, attributed to the field it degrades. The control never renders an error of its own, and never rewrites the stored value.

## Known Limitations

- Every message the Schema reports *below* the field's own node — an over-`max_depth` branch, a required Attribute — is shown under the tree rather than on the row or the Attribute that caused it. Deduplicated by text; the paths are in `formState.errors` for a Consumer that wants to point at rows.
- The drawer always adds at the root; a new Reference is nested by dragging it.
- An Attribute is checked by the Schema but nothing shared validates the Attribute *Spec* — a hand-written duplicate accessor among Attributes goes unreported (ADR-0007, above).
- `select`, `radio` and `checkboxes` have no settings editor anywhere in fieldkit, so their options cannot be authored in the panel — an Attribute of one of those types needs its `settings.options` hand-authored. Not specific to Attributes.
- Attributes are not reorderable in the settings list; they render in declaration order.
- The row's filled count does not say which Attribute is *invalid*, only how many are filled.
- A stored pin is not shown on the row; it is chosen when the Reference is added and changed by removing and re-adding it. Read mode does not show it either.
- The browse drawer's page size is fixed at 10.
- Very large trees are not virtualised.
