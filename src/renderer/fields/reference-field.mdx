# Reference

A **Reference Tree**: References to other Contents, ordered and nested. Each row shows the referenced Content's *current* name, resolved through the `reference` adapter; adding one opens a drawer that browses the catalogue. Requires a `reference` adapter configured via `FieldKitProvider`.

## When to Use

Use **Reference** when a field holds several links to other Contents — "Related articles", "Cited works", "Featured items" — and when the arrangement of those links is itself meaningful. For exactly one Reference, use [Single Reference](?path=/docs/fields-single-reference--docs), which is a separate field type because the two store incompatible values (ADR-0005).

Each Reference can also carry **Attributes** — values about the pointing itself rather than about either Content, such as the page a citation appears on. See [Attributes](#attributes).

## The Tree

Every row carries a drag grip. Dragging a row reorders it among its siblings; dragging it rightwards nests it under the Reference above, one level per `24px` of travel. **A Reference's descendants travel with it** — a branch keeps its shape however far it moves.

A drag can also gain children. A **leaf** dropped one level *shallower* than the row below it takes that row, and its branch, as its own — **Adoption** (ADR-0012), on the same terms inserting follows, so the two paths agree about whether it exists at all. Only a leaf may: a Reference carrying children of its own keeps the older floor, the row below's own depth, because it cannot take a branch while bringing one. `max_depth` still wins over the floor — a drop may not adopt its way past the ceiling, and where a tree already breaks it the adopting level is withdrawn rather than offered on a branch no placement could make legal.

Because adoption restructures rows the Author never picked up, the drag **says so before the release**: every row a release would take is outlined, and the tree announces how many — "Adopting 2 References". A folded Reference is outlined once and counted once, standing in for its branch exactly as it does everywhere else here. That announcement is part of the rule and not decoration; without it the behaviour is indistinguishable from the knkCMS core defect it was modelled on. It is reachable from the keyboard on the same terms, <kbd>←</kbd> being the one press that finds the adopting level.

A drag also shows **where** it will land and **at what level**. A line — 3px in the accent colour with an end-dot, matching the specification editor's canvas — appears in the gap the release would land in, indented to the depth it would land at; the dragged row follows the pointer through the list, indented to that same depth. The two say one thing from two places on screen, both read off the resolution the release itself performs, so the line can only ever draw a landing the drop rules already allow. It is drawn for a **re-indent in place**, where nothing else on screen moves — the case that most needs it, and one knkCMS core cannot perform at all — and it is *not* drawn when the landing is the row's current slot and depth, because that release writes nothing. The dragged row's transform carries the drag's vertical travel only: its indent is the level, and an unquantised sideways slide on top of a 24px indent step buries the answer under the pointer's position.

**Everything else holds still.** No row displaces to open a gap for the one in flight — the line alone says where the drop lands, and the dragged row alone says at what level. The dragged row is therefore **lifted rather than dimmed**: opaque, raised above its neighbours and shadowed, so it reads as a card being carried over the rows. With no gap opening beneath it, it visibly overlaps the rows it passes, which is accepted deliberately. The alternative is worse: a list that both parts *and* springs a folded branch open moves twice for one gesture, and the row that moves is the one being aimed at.

A Reference with children carries a chevron that folds its branch away, so one branch can be worked on without the rest in the way. A tree of more than `REFERENCE_TREE_COLLAPSE_THRESHOLD` References **opens with every parent collapsed**; at or below it, expanded. The threshold is a provisional guess and wants tuning against a real Spec. Folding is the control's own state and is never stored.

Folding and dragging agree on two rules. A folded Reference **stands in for its whole branch**: dropping below one lands below everything it hides, and a drop can reach a depth of "child of the folded Reference" but never deeper — a drop may only land somewhere an Author can see. And whatever a Reference lands *inside* is **unfolded on the drop**, so it is visible where it went.

A drag also **changes what is folded, for as long as it runs**. Lifting a Reference folds its own branch away and restores it on the drop or the cancel; only that branch, and no other Reference's fold moves. Its descendants were never legal targets — a Reference cannot be dropped inside its own branch, because the projection takes that branch out of the list before reading the neighbours either side of the landing — so what folding does is *say so*, leaving every row on screen a row a release could land against. It cannot loosen `max_depth`: a branch's height is measured from the tree, never from what is on screen, so a folded branch is exactly as tall as it was.

The inverse holds too. A folded Reference is a legal target, but a slot *inside* it is unreachable while it stays shut — so **resting a pointer drag on one for `SPRING_DWELL_MS` opens it**, the same dwell and the same feel as the specification editor's spring-loaded tabs. **A spring is a preview until the drop commits:** a Reference that sprang open and did not receive the drop is folded again when the drag ends, and <kbd>Esc</kbd> restores every fold — the dragged branch's and any sprung one's — to what it was at the lift. The one that *received* the drop stays open, which is the unfold-on-arrival rule above.

Dragging works from the keyboard as well as the pointer: focus a grip, press <kbd>Space</kbd> to lift, <kbd>↑</kbd>/<kbd>↓</kbd> to move between rows, <kbd>←</kbd>/<kbd>→</kbd> to change how deeply the drop nests, then <kbd>Space</kbd> to drop or <kbd>Esc</kbd> to cancel. A keyboard drag has **no dwell** and needs none: arrowing onto a Reference is deliberate already, and a keyboard drop into a folded branch lands at its end and unfolds it.

The depth a drop lands at is decided by **pure functions** in `src/schema/reference-tree.ts` — read the stored value, flatten, project a depth, move the branch, re-nest, write back — so none of the drag arithmetic is asserted through a DOM.

There is no pagination, deliberately: it cannot coexist with dragging to a position nobody can see.

## Adding a Reference where it belongs

An **insertion strip** sits in the gap between every pair of rows on screen, and before the first — so every position is reachable, including the top of the tree, which knkCMS core's equivalent cannot reach. Pointing at one grows it and draws a line at the depth a new Reference would land at; moving the pointer sideways changes that depth, one level per `24px` indent step. Clicking opens the same browse drawer the Add control does, and the Content lands at that position and that depth.

The strip **says what it will do** — the sentence it shows is also its accessible name, so the two cannot drift apart:

| The strip reads | What it means |
|---|---|
| `Insert as a child of X` | One level deeper than the row above: X's first child |
| `Insert as a sibling of Y` | At an existing rank: Y is the Reference it would follow, or — before the first row of that rank — the one it would precede |
| `…, adopting 2 References` | Landing shallower than the rows below takes them as children. See [Adoption](#adoption) |

It names **what it actually names**: the sibling in the sibling case, the parent in the child case. Core names the prospective *parent* in both, so its strip can read "+ Add sibling of A" while re-parenting A's whole branch.

That same sentence is repeated as a **header line in the add drawer**, through both of its steps — see [the drawer's chrome](#the-drawers-chrome-steps-and-destination). It is carried across rather than composed a second time (`reference-destination.ts` is the one place it is built), because two wordings of one fact are free to disagree.

The depth on offer is bounded by the row above (nesting may not skip a level), by the row below (the floor), and by `max_depth` — all of them `projectInsertDepth`'s answer, the same model the drag reads with a different pair of neighbours. Inserting **under a folded Reference** lands at the end of its branch and unfolds it, exactly as a drop into a folded branch already does.

At `max_items` the strips are disabled, on the same terms the Add control is — an unset cap is no cap. While a drag is running they are replaced by inert spacers of the same height — except the one gap the release would land in, which draws the landing line described above — so two insertion affordances never compete for one gap, and the list jumps neither when a row is lifted nor when the landing moves from one gap to another.

The **Add control stays**, and appends at the root. It is the way into an empty tree, which has no gaps to put a strip in. Its append is put into the same words as a strip's — `Insert as a sibling of <last root>`, or `Insert as a root Reference` on an empty tree — so the drawer it opens says where the Reference is going rather than nothing.

### Operating a strip from the keyboard

Everything a strip does with a pointer it does without one. <kbd>Tab</kbd> reaches it — focusing it grows it and shows the same prospective insertion, sentence and all, that hovering does — then <kbd>←</kbd>/<kbd>→</kbd> change the depth one level per press, <kbd>Enter</kbd> opens the browse drawer, and <kbd>Esc</kbd> leaves the strip without inserting.

The depth semantics are identical; only the input differs. Both write the same offset and read `projectInsertDepth` over it, so an arrow press cannot reach a level the pointer could not, and the bounds bind in the same places. This is the drag's keyboard story with a different pair of neighbours — there <kbd>←</kbd>/<kbd>→</kbd> map to one indent of the very travel a pointer would make — and it is why the strip is a real button rather than the styled div knkCMS core's is: core registers a `PointerSensor` only and its strip has no key handling at all, so nesting is unreachable there without a pointer.

An arrow press moves the *level*, not the offset behind it, so pressing <kbd>→</kbd> three times against a ceiling of one does not bank two presses that a later <kbd>←</kbd> has to spend before anything moves.

<kbd>Esc</kbd> **leaves** the strip — focus goes with it, which is what leaving means, at the cost of the browser restarting <kbd>Tab</kbd> from wherever it puts the focus next. It is also **contained**: it goes no further. A Reference Field rendered inside a drawer — `EditDrawer` renders one through `SpecForm` — must not lose its edits to the press that backed out of a strip, and dismissable layers read Escape off `document` in the capture phase, so the strip answers it a phase earlier still. Only an Escape aimed at the strip is taken; anything else travels untouched, including the one that cancels a keyboard drag.

Each strip is **its own tab stop**, in document order among the rows — so an `N`-row tree carries `N+1` of them, interleaved. The alternative, one roving tab stop for the group, was considered and rejected: every other control in this tree — the grips, the chevrons, the Attributes and Remove buttons — is individually focusable, and a strip that answered to <kbd>↑</kbd>/<kbd>↓</kbd> instead of <kbd>Tab</kbd> would be the one thing here that did. A strip disabled at `max_items` is skipped entirely rather than offering a stop that does nothing, and keeps the reason as its accessible name.

Depth changes are **announced**. The sentence is the strip's accessible name, so arriving on one reads it out; each arrow press after that also goes to a live region under the tree, because a name that changes under standing focus is the case a screen reader announces least reliably. Arriving does not use the live region — it would say the same sentence twice.

### Adoption

A Reference arriving **shallower than the rows below it** takes them, and their branches, as its children. Inserting a root between a Reference and its children therefore gives the new Reference those children. This is deliberate (ADR-0012) and matches core, so an Author working in either system gets one answer.

It is not an operation anything performs: `spliceReference` puts one entry in the flat list and moves nothing, and `nestReferences` reads order and depth alone — so the rows that follow a shallower entry *are* its children. There is no ancestor surgery, and an orphan stays unrepresentable.

Because it restructures rows the Author never pointed at, it is **announced before the click** — that announcement is part of the decision, not decoration. The count is of rows **on screen**: a folded Reference counts as one and brings its branch, which is the same rule folding and dragging already agree on.

Adoption cannot make a tree too deep. Splicing moves no other row, and a row is adopted only when it is already deeper than the arrival, so re-nesting never pushes an existing row down. What `max_depth` does withdraw is the offer to rearrange a branch on a tree that *already* breaks the cap, where no placement could make it legal.

## Finding a Reference the tree already holds

A Field past `REFERENCE_TREE_COLLAPSE_THRESHOLD` — the same number that decides a tree opens collapsed — carries a **Find** control above the tree. Type the display name of a Content and it lists the References *in this tree* that match, each under the path of ancestors leading to it. At or below the threshold there is no control at all: a tree an Author reads at a glance does not need one.

Matching is **case-insensitive substring** against the resolved display name, over **every** Reference at every level rather than the rows a fold set leaves on screen — a collapsed branch hiding the answer is the problem Find exists for. It happens in the browser, over the names the Field has already resolved (ADR-0013); the Adapter is not asked. A row whose Content did not resolve shows its id, and Find matches that id, so the control can always find what is on screen. The same Content sitting in the tree twice gives **two results**, told apart by their paths.

Picking one **Reveals** it: every fold above it opens, the row scrolls to the centre of the viewport, takes focus, and stays marked until the next Reveal. The row itself takes `tabIndex={-1}` — it never joins the tab order, and landing on it puts its grip, its fold control and its buttons one <kbd>Tab</kbd> away, in the order they are drawn. The Reveal is announced in a live region as well as marked on the row.

**A Reveal is not a preview**, in deliberate contrast to a Spring. It opens the ancestors that are shut and touches nothing else, so Reveals **accumulate**: an earlier Reveal's folds stay open, a fold an Author opened by hand is never fought, and the revealed Reference's own branch stays as it was — showing a row and opening what hangs under it are different questions.

Find **never filters or restructures the tree**, and writes nothing: order, nesting, Pins and Attributes are untouched, so a drag is never standing on ground that moved. It claims **no global keyboard shortcut** — the form's own field search claims `/` on a first-mounted-wins basis, and a rival listener here could never fire. <kbd>Esc</kbd> dismisses the results and is contained, so a Field rendered in a drawer does not lose its edits to the press that shut a dropdown.

The matching and the ancestor paths are pure functions in `src/schema/reference-find.ts`, and which folds a Reveal opens is `foldsToReveal` in `src/schema/reference-tree.ts` — so none of it is asserted through a DOM. A Consumer driving `ReferenceTree` itself passes a `reveal` — a row key and a token together, because the token is what makes asking for the same Reference twice running two Reveals, and a key with nothing to arm it would silently do nothing the second time.

**Read mode carries the same control**, on the same threshold and over the same functions — see [Table Cell and Read Mode](#table-cell-and-read-mode). Locating a Reference never requires switching into an editable view.

## Value

Fieldkit owns the shape; a Consumer maps it to whatever it persists (ADR-0008).

```ts
// The stored value
Reference[]

interface Reference {
  id: string                            // the referenced Content
  pin?: string | null                   // the Pin's target id; absent = newest Version
  attributes?: Record<string, unknown>  // keyed by the Attribute's accessor
  children?: Reference[]                // the branch under this Reference
}
```

The nesting is genuine rather than a flat list with ancestor ids, which is what makes an orphan unrepresentable. Flat encodings are the Consumer's business.

Form data is only as well-formed as whatever produced it, so a stored entry that is not a Reference renders no row. Removing and dragging both leave such an entry at the top-level position it held; one nested inside a branch does not survive a drop, because every branch is rebuilt from depths — and a value holding one cannot pass the Schema anyway.

A display name is **never stored**. Names are resolved through the adapter on every load, so a Content renamed elsewhere reads correctly here, and one that no longer resolves keeps its id on screen rather than vanishing.

Names are resolved for **every Reference at every level**, including the ones inside collapsed branches (ADR-0013), and the ids go out in **batches**: fieldkit cuts the list into calls of a fixed maximum size and merges the results, so `fetch` may be called several times for one tree — concurrently — and is never handed ten thousand ids at once. The batch size is fieldkit's, not the adapter's — nothing is asked of a Consumer, and an adapter written against a field of twenty References keeps working at ten thousand. A batch that rejects is reported through `onError` once and costs only its own names: the rows the other batches resolved still read normally, and the rest fall back to their ids. The size is a **provisional** number, a guess rather than a measurement; it is `REFERENCE_NAME_BATCH_SIZE` in `renderer/hooks/batch-ids.ts`, internal rather than a knob, and the first Consumer to measure it should change it there.

`pin` holds **only the target id**. Which *kind* of target it is comes from the field's `pin_mode`, never from the value (ADR-0008) — which is why changing `pin_mode` invalidates every stored pin at once rather than leaving some stale. No pin at all means the Content's newest Version.

## Settings

| Setting      | Type                               | Default  | Description                                                        |
|--------------|------------------------------------|----------|--------------------------------------------------------------------|
| `blueprints` | `string[]`                         | `[]`     | The blueprints this field may point at. Empty means the adapter decides |
| `max_items`  | `number`                           | —        | At most this many References, counted over the whole tree — a nested child counts as much as a root |
| `max_depth`  | `number`                           | —        | How many **levels** the tree may hold, roots being level 1. `1` is a flat list; `2` allows one level of nesting |
| `pin_mode`   | `"none" \| "release" \| "version"` | `"none"` | Whether References are fixed to a release, to a version, or track the newest version. Absent reads as `"none"` |
| `attributes` | `Field[]`                          | `[]`     | The Attribute Spec — the Fields every Reference carries about the pointing. See [Attributes](#attributes) |

`max_depth` is a **count of levels, not the index of the deepest one** — the dialect every other `max_*` setting in this package speaks, and the one knkCMS core's `reference` speaks too. The tree model works in 0-based depth indices, so the conversion happens once, in `referenceDepthCeiling()`; `referenceItemCap()` is its twin for `max_items`. Read both through those functions rather than with `?? 0`: **an unset cap is no cap**, and `0` is a cap of zero. Conflating the two is how an uncapped field ends up refusing to add anything.

The Blueprints control is the shared `BlueprintPicker`, so it falls back to blueprint-id entry when the blueprint adapter cannot enumerate blueprints. Each cap is a number box whose empty state means "no limit" — emptying it removes the key rather than storing `0`. `pin_mode` is a select, with a warning that changing it strands every pin already saved — fieldkit cannot refuse the change, because only a Consumer knows whether any Content would be stranded (ADR-0008); a Consumer freezes the setting through `config.locked_settings` instead.

## Attributes

An **Attribute** is a value a Reference carries about the *pointing* — the page a citation appears on, the role a credit names — not about either Content. An Author declares them once per field, as a Spec of ordinary Fields, so "page" can be a number and "role" a select and either can be required. Someone filling in the form opens a drawer per Reference and fills them in with real controls.

Values are stored **keyed by Accessor** on the Reference itself, which is what makes them survive: moving a Reference moves its whole entry, Attributes included, so nothing has to keep a parallel structure in step. In knkCMS core these are bare strings positionally aligned to a settings array.

Each row shows a **filled count** — `1/2` — so it is visible at a glance which References still need attention. The count is over exactly what the Schema composes: a hidden Attribute, a value-less Marker a hand-written Spec slipped in, and an entry that is not a Field at all are none of them counted, asked for, or composed — a stray costs itself and nothing else. A key left behind by an Attribute since deleted is not counted either. `false` and `0` count as filled: they are what an unchecked box and a zero page number are, and the count must not disagree with the Schema about whether a required Attribute is satisfied. A field declaring no Attributes shows no affordance at all.

### Authoring them

The Attribute Spec is authored in the config panel's **Type settings** tab. Adding one is the ordinary type picker; configuring one is the panel's incumbent **drill-in** — the same Back control, the same three tabs, the same accessor gate a group's child gets. There is no separate nested editor.

The picker offers strictly less than the canvas does, through a new `FieldContext` value, `"attribute"`:

- **no Markers** — a drawer has no Tab and no Card for a Section or a Card to open;
- **no containers** — `group`, `fieldset` and `blocks` would be composed but never checked (see the boundary below);
- **no reference types** — cycle rejection walks `children`, so a Reference Field declared as an Attribute is a recursion nothing would catch.

### The settings-nested boundary (ADR-0007)

The Attribute Spec lives in `settings.attributes`, following the Blocks precedent, and inherits ADR-0007's boundary **verbatim**. `resolveSpec()`, `validateSpec()` and `resolveMarkerConvention()` walk `Field.children` only, so nothing shared reaches an Attribute Field. Concretely:

- a **duplicate accessor** between two Attributes is never reported — the later one silently wins the composed shape (the editor generates unique accessors, so only a hand-written Spec can produce one);
- an **empty name** and an **empty accessor** are never reported either;
- a **Fieldset** declared as an Attribute is never resolved, and composes as the opaque record any unresolved Fieldset does — which is why the picker does not offer one.

The reference plugin composes the Spec itself, exactly as the Blocks plugin composes a block type's fields. Composing is not walking, so the boundary is unmoved. `src/schema/reference-attributes.ts` is where this is written down.

## Pinning, and the drawer's second step

When `pin_mode` is `"none"` the add drawer has **exactly one step**: picking a Content stores `{ id }` and closes, and the adapter is never asked about pin targets.

When the field pins, picking a Content opens a **second step** listing what that Content may be pinned to. Choosing a target stores `{ id, pin }`; choosing **Newest version** — always first, and available even while the targets load or after a lookup that failed — stores `{ id }` with no `pin` key at all. **Back** returns to the browse, still narrowed to whatever was searched, having stored nothing.

## The drawer's chrome: steps, and destination

Two things the drawer says about itself, above whichever step is showing.

**Its steps**, through anker's `Stepper`. The titles are `Choose content` and — when the field pins — `Choose a release` or `Choose a version`, whichever `pin_mode` named. The active step carries `aria-current="step"`, anker's accessibility rule for the component (its README, *Accessibility*); `StepperStep` sets it itself, and the controlled `step` index is what makes the mark follow the flow instead of resting on step one.

The step **count** follows `pin_mode` alone, exactly as the flow does. Whether the Stepper is *there* does not: it renders in the one-step flow too, so the drawer's chrome does not change shape depending on a field setting.

**Where the Reference will land**, as a header line under the steps and shown through both of them. It is the same sentence the [insertion strip](#adding-a-reference-where-it-belongs) carried — the Reference the new one will sit under or beside, and the rows it will adopt where any would. The strip's own label is off the screen by the time this is read, and the drawer is where the decision is committed, so the sentence is handed across on the `ReferenceInsertRequest` rather than rebuilt from neighbours that have since been re-indexed.

The Add control, which never announced anything, gets the same treatment: `describeAppend` puts its root append into the same words.

## Adapter Interface

```ts
reference: {
  search: (query: ReferenceSearchQuery) => Promise<ReferenceSearchResult>;
  fetch: (ids: string[]) => Promise<ReferenceItem[]>;
  listPinTargets?: (              // optional
    contentId: string,
    mode: "release" | "version",
  ) => Promise<PinTarget[]>;
  getSearchFilters?: () => Field[];   // optional
  getResultColumns?: () => Field[];   // optional
}

interface PinTarget {
  id: string;            // what `pin` stores
  label: string;         // what the person reads
  description?: string;  // a second line, where one helps
}

interface ReferenceSearchQuery {
  blueprintIds: string[];
  query: string;
  filters: Record<string, unknown>;   // opaque to fieldkit
  excludeIds?: string[];              // optional — already referenced
  page: number;                       // 1-based
  page_size: number;
}

interface ReferenceSearchResult {
  items: ReferenceItem[];
  total: number;                      // across every page
}
```

`search` is a query object rather than positional arguments because a browsable picker over a real catalogue needs pagination and a total, which the old bare-array signature could not express (ADR-0009).

### The adapter describes itself with Specs

Filtering and columns mean domain nouns — a status, an assigned user — that fieldkit's catalogue must not learn. So the adapter describes them instead: `getSearchFilters()` returns the `Field[]` describing a query, `getResultColumns()` returns the `Field[]` describing one Content row. Fieldkit renders the first with `FieldRenderer` and the second with `SpecDataTable`, so each field type brings its own control and its own cell for free.

The values the filter form collects travel back through `search` as `filters` — **an opaque record fieldkit never inspects**. A filter no field type can express needs a new field type rather than a bespoke control.

Both methods are **optional**. Without them the picker degrades to a search box and a name column, which is what a Consumer that has not implemented them should get rather than an error.

### Contents already in the tree

The picker does not offer a Content the field already holds — adding it again would put the same Content in the tree twice. The ids travel with the search as `excludeIds`: **every Reference at every level**, not just the roots, deduplicated, and read from the same flattening `max_items` counts.

The field is **optional and additive**, on the same terms as the methods above. An adapter that honours it excludes them at the source, so its `total` counts exactly what it returned. An adapter that ignores it is not wrong, only less precise: fieldkit drops them from the page it was handed either way, so the picker still offers none of them — but the total is the adapter's, so it still counts the Contents nobody can pick. A Consumer written before the field existed keeps working unchanged.

This is a **policy about the picker, not about the value**. A Reference Tree keys its rows by path precisely so the same Content *can* appear twice; nothing here refuses such a value, rewrites one, or stops a drag producing one. [Single Reference](?path=/docs/fields-single-reference--docs) applies the one-item version of the same rule.

`listPinTargets` is **optional on the same terms**. Only the adapter knows a Content's Releases or Versions, and it is the adapter that normalises whichever kind was asked for into an id, a label and a description — so **fieldkit models neither a Release nor a Version**. Without the method a pinning field offers the newest Version and nothing else: the same answer a Consumer gets from returning an empty list, and the same one the field already shows while the targets are in flight. A Consumer that has not implemented pinning gets that rather than an error.

The absence is **silent** — it is a configuration, not a failure — where a call that *rejects* is reported through the provider's `onError`. It is called only when the field pins, and only once a Content is chosen.

## Validation

| Rule        | Description                                              |
|-------------|----------------------------------------------------------|
| `required`  | At least one Reference                                    |
| per item    | Each entry must be a Reference — an object with a non-empty `id` |
| per branch  | A nested Reference is held to the same rules as a root one |
| per Attribute | Each declared Attribute is checked as the type it is; a required one blocks submit and reports at its own key under the Reference that owns it |
| `max_items` | The flattened tree holds at most that many References. Reported **at the field's path** |
| `max_depth` | No Reference sits deeper than that many levels. Reported **at the offending Reference's path** — `related.0.children.1` |

```ts
// Optional
z.array(referenceTreeSchemaWith(attributes)).superRefine(caps)

// Required
z.array(referenceTreeSchemaWith(attributes))
  .min(1, "Related articles is required")
  .superRefine(caps)
```

The node schema is **lazily recursive**: it names `children`, so a nested branch survives a parse. An object schema that did not would strip the branch, and a drop that nested a Reference on screen would submit a flat list. The recursion is also what puts the Attribute Spec on every Reference at every level.

`attributes` is the Attribute Spec composed through the plugin's `composeChildren` argument (ADR-0007), and takes one of three shapes:

- **no Attribute declared** — the opaque `Record<string, unknown>` ADR-0008 declares, unchanged from before Attributes existed;
- **no required Attribute** — the composed object, optional and `passthrough`, so a Reference carrying nothing stores no `attributes` key at all;
- **a required Attribute** — the same object with a `{}` default, so a Reference added before the Attribute was declared cannot slip past the check.

`passthrough` throughout, as both container types do: a stored record carries keys the Spec no longer declares, and validation arriving is no reason to prune an Author's data. A required Attribute reports at `related.0.attributes.role` — under the Reference that is missing it — and at `related.0.children.0.attributes.role` for a nested one.

The blast radius mirrors ADR-0007's: declaring a required Attribute starts checking every stored Reference of that field, so data that saved successfully before can begin blocking submit.

Both caps live in the **Schema**, not only in the control, so an import or an API write is checked on the same terms a form is. The UI additionally disables the add affordance at `max_items` and clamps a drop to `max_depth`, but neither is where the rule lives.

That has a blast radius, and it is intended: **a Spec whose caps were never enforced can begin blocking submit on data that saved fine before.** What does not happen is fieldkit quietly fixing it — a value over a cap is reported, never truncated, and a branch past the depth is reported, never re-nested. Only the shallowest Reference in each over-deep branch is reported, since everything under it is too deep because of it.

`ReferenceField` renders those messages under the tree, because `FormField` shows only the message on the field's *own* node and `max_depth` deliberately reports deeper. The same collection catches a required Attribute, which reports at `related.0.attributes.page` for the same reason — and which lives inside a drawer, so without it a submit blocked by an Attribute would be a submit blocked by nothing visible at all.

## Table Cell and Read Mode

`ReferenceCell` renders a count — "3 references" — at table density, counting **every** Reference at every level, exactly as `max_items` does. Not the names: a cell has neither adapter access nor async, so the alternative is a row of raw ids. `SingleReferenceCell` counts on the same terms ("1 reference"), so the two types read alike in one table.

Read mode bypasses the cell and renders the tree instead: `ReferenceReadValue` resolves every Content's current name through the adapter, indents each Reference to its depth, and shows each Reference's Attribute values against it. It sits inside the renderer, so it reaches the adapter and has the height a table row does not (ADR-0008). It never touches react-hook-form, so read mode still needs no `FormProvider`.

It **folds and finds on the same terms the editable tree does**. Past `REFERENCE_TREE_COLLAPSE_THRESHOLD` a read-mode tree opens with its parents collapsed and carries the Find control; at or below it, expanded and without one. Folds open and close while reading, because reading a folded branch is reading, and picking a Find result Reveals the Reference exactly as it does when editing — every fold above it opens, the row scrolls to the centre, takes focus and stays marked. Nothing about any of it is written: folding and the mark are the component's own state, as folding already is on the editable side.

The two renderers stay separate components — one has grips, drags and springs, the other has none of them — but they call one implementation of the rules they share: `initialReferenceFolds`, `visibleReferenceRows` and `foldsToReveal` in `src/schema/reference-tree.ts`. That is what makes "the same tree does not behave like two different trees" a fact rather than a promise, and it narrows #88 without closing it.

The bypass is the plugin's own `readComponent` rather than a `field_type` branch in read mode's code (ADR-0007). For reference types that is not merely tidier but necessary: a minted type carries its own id, which no list of names in shared code could contain, so `toc_reference` gets the same read mode `reference` does.

## Minting a reference-shaped type of your own

The catalogue stays generic, but it exports the parts (ADR-0010). A field type whose meaning is *your* domain — a table-of-contents reference, a publication tree — is a `createReferencePlugin()` call rather than a rebuilt tree:

```ts
import { createReferencePlugin } from "@knkcs/fieldkit/schema";
import { BookOpen } from "lucide-react";

export const tocReference = createReferencePlugin({
  id: "toc_reference",              // what a Spec stores, and what a backend addresses
  name: "TOC Reference",
  description: "The publication tree this Content hangs in",
  icon: BookOpen,
  maxPerSpec: 1,                    // one per blueprint
  availableIn: ["blueprint"],
});
```

Pass it to `FieldKitProvider` and `TypePicker` beside `builtInFieldTypes` and it behaves as a built-in does: the same tree, the same browse drawer, the same count cell, the same read mode, the same settings editor, the same Schema. Only the catalogue entry is yours — `id`, `name`, `description`, `icon`, `category`, `maxPerSpec`, `availableIn`, and `defaultSettings`, which is merged **over** the reference defaults so naming blueprints does not silently turn pinning on.

`maxPerSpec` is enforced everywhere it always was: `validateSpec()` reports a second instance, the type picker greys the type out once one exists, the canvas blocks the duplicate, and `SpecEditor` refuses to save.

**Registering a replacement is not a migration.** Fieldkit's removed `toc_reference` stored a bare id string; a minted type stores a Reference Tree, so stored values have to be converted — `"x"` becomes `[{ id: "x" }]` — or they fail the Schema and render as an empty tree. Its `always_latest` and `attributes` settings keys are gone with it; `pin_mode: "none"` is what `always_latest` meant.

For a control of your own around the same tree, `ReferenceTree` is exported from `@knkcs/fieldkit/renderer`. It is the rows and the dragging, not the Field: it takes `rows` (from `readReferenceTree(value)`), the stored `value`, an `onChange` that receives the whole next value, `names` — a record keyed by Content id — and `depthCeiling`, a 0-based depth index that `referenceDepthCeiling(settings)` converts a `max_depth` setting into. Resolving those names, and offering any way to *add* a Reference, stay yours, because only your Adapter can do either.

The insertion strips are the same bargain. Pass `onInsert` and the tree renders them; it is called with a `ReferenceInsertRequest` — where the Reference would go, at what depth, the `destination` sentence the strip just announced, and a `commit` that puts one there once your own browse has produced it. Show `destination` in whatever you open: it is what an Author already read, and re-phrasing it is how the two come to disagree. The write stays in the tree because folding has to follow it. Without `onInsert` there are no strips. `atItemCap` disables them, and should be read through `referenceItemCap(settings)` — an unset `max_items` is no cap, never a cap of zero. `readReferenceTree`, `countReferences` (every Reference at every level, what `max_items` caps), `referencesPastDepth` (where a tree breaks `max_depth`), `referenceItemCap` and `referenceDepthCeiling` all come from `@knkcs/fieldkit/schema`.

## Errors

An adapter failure reaches the Consumer's `onError` on `FieldKitProvider`, attributed to the field it degrades. The control never renders an error of its own, and never rewrites the stored value.

## Known Limitations

- Every message the Schema reports *below* the field's own node — an over-`max_depth` branch, a required Attribute — is shown under the tree rather than on the row or the Attribute that caused it. Deduplicated by text; the paths are in `formState.errors` for a Consumer that wants to point at rows.
- An Attribute is checked by the Schema but nothing shared validates the Attribute *Spec* — a hand-written duplicate accessor among Attributes goes unreported (ADR-0007, above).
- `select`, `radio` and `checkboxes` have no settings editor anywhere in fieldkit, so their options cannot be authored in the panel — an Attribute of one of those types needs its `settings.options` hand-authored. Not specific to Attributes.
- Attributes are not reorderable in the settings list; they render in declaration order.
- The row's filled count does not say which Attribute is *invalid*, only how many are filled.
- A stored pin is not shown on the row; it is chosen when the Reference is added and changed by removing and re-adding it. Read mode does not show it either.
- The browse drawer's page size is fixed at 10.
- When the adapter ignores `excludeIds`, the backstop shortens each page after it was cut, so a page can show fewer than 10 rows — or none at all, if a field already references ten Contents that land on the same page — while the total still promises more. Honouring `excludeIds` removes this entirely.
- Very large trees are not virtualised.
- Find reports "No matching References" while the names are still arriving, rather than saying they are still arriving. It also matches neither diacritic-folded text ("muller" does not find "Müller") nor a resolved Reference's id — an id matches only where no name resolved, which is what the row is showing anyway. All three are ADR-0013's rules and are not yet built.
