# Fieldset

A Fieldset names a Blueprint and renders that Blueprint's Fields inline, as one
non-repeating record nested under the Fieldset's own Accessor. A form user sees
ordinary Fields — collapsible where the Author asked for it.

## When to Use

Use **Fieldset** for a shared sub-record that several Specs embed: an address, a
contributor, a set of publishing dates. Editing the Blueprint updates every Spec
that embeds it, which is the whole point of the type — and the reason its Fields
are fetched rather than copied into the Spec (ADR-0003).

For a repeating record use [Group](?path=/docs/fields-group--docs); for a purely
visual grouping that produces no value, use a Card marker.

## Settings

| Setting       | Type      | Default | Description                                          |
|---------------|-----------|---------|------------------------------------------------------|
| `blueprint`   | `string`  | —       | Id of the Blueprint whose Fields are embedded.       |
| `collapsible` | `boolean` | `false` | Lets a form user fold the embedded Fields away.      |

Both keys match knkCMS core's `fieldset` settings, so seeded specs migrate
without a rewrite.

The Author picks the Blueprint in the config panel from whatever
`adapters.blueprint.list()` returns — see
[Listing the Blueprints an Author may embed](#listing-the-blueprints-an-author-may-embed).

## Listing the Blueprints an Author may embed

The blueprint adapter has an **optional** list capability. Where it exists, the
Fieldset's config panel offers those Blueprints by name; where it does not, the
panel falls back to Blueprint id entry:

```ts
// BlueprintSummary is exported from both /schema (beside
// BlueprintSchemaAdapter) and /renderer (beside FieldKitAdapters).
import type { BlueprintSummary } from "@knkcs/fieldkit/schema";

const adapters = {
  blueprint: {
    getSchema: (id) => api.blueprintFields(id),
    getData: (id, query) => api.blueprintRecords(id, query),
    // Optional. Omit it and nothing breaks — the Author types an id instead.
    list: async (): Promise<BlueprintSummary[]> =>
      api.blueprints().map(({ id, name }) => ({ id, name })),
  },
};
```

Fieldkit does no filtering of its own — it has no notion of a Blueprint kind
(ADR-0002). Return exactly the Blueprints this Author may embed; knkCMS core,
for instance, narrows to its `fieldset` blueprint type on its side.

What the panel does with the result:

- Picking a Blueprint stores its `id` in `settings.blueprint`; clearing the
  selection removes the setting, and the Field goes back to
  "No blueprint selected".
- A stored Blueprint the list does not offer — one since deleted, or one this
  Author may no longer embed — stays selected under its raw id rather than
  being silently dropped.
- A `list` that rejects goes to the `FieldKitProvider`'s `onError`, named for
  the Fieldset it leaves unconfigurable, and is then treated as no capability
  at all: the Author gets id entry and can still finish the job. With no
  `onError` configured it reaches the console instead, so the degrade is never
  silent.
- The list is fetched once per config-panel mount; it is not cached across
  fields.

`SpecEditor` reads this through the consumer's `FieldKitProvider`, which it must
already be mounted inside.

## Where the Children Come From

A Fieldset's children are **never stored in the Spec**. There are two paths:

1. **Resolved** — the Consumer ran `resolveSpec()` and the Fieldset arrives
   with `children` already attached. Nothing is fetched.
2. **Self-resolved** — the Consumer did not, so the component fetches
   `adapters.blueprint.getSchema(blueprint)` itself, **for display only**.

Path 2 is a documented degrade, not a supported mode: fields resolved that way
render and hold values, but the Consumer generated their Zod Schema before
those Fields existed, so **nothing about them is validated** — a required child
does not block submit. Resolving is what puts them in the Schema (ADR-0004), so
a Consumer who needs validation resolves first.

With no blueprint adapter configured at all, the established
"Blueprint adapter not configured" stub renders and the rest of the form works
unchanged (ADR-0003). With no Blueprint chosen, the Field says
"No blueprint selected" rather than rendering an empty frame.

### Resolving the Spec

`resolveSpec()` is the step between loading a Spec and building its Schema
(ADR-0004). It takes the same adapters object the provider gets, so a Consumer
calls it unconditionally rather than knowing which Field types need fetching:

```ts
import {
  getDefaultValues,
  resolveSpec,
  specToZodSchema,
} from "@knkcs/fieldkit/schema";

const spec = await resolveSpec(authoredSpec, adapters);
// Both read the Resolved Spec: children the Schema never saw are neither
// validated nor seeded.
const schema = specToZodSchema(spec, plugins);
const defaultValues = getDefaultValues(spec, plugins);
```

What it guarantees:

- Every Fieldset gets its Blueprint's Fields as `children`, recursing into
  Fieldsets those Blueprints embed and into Fieldsets nested in a Group's
  children.
- One `getSchema` call per Blueprint id per call, however many Fieldsets name
  it.
- A Blueprint that transitively embeds itself **throws**, naming the chain
  (`Fieldset blueprint cycle detected: person_bp → address_bp → person_bp`)
  rather than recursing forever.
- An adapter rejection propagates untouched — it never becomes empty children.
- A Spec with nothing to resolve comes back as the same array, so calling it on
  a Fieldset-free Spec costs nothing and changes no identity.
- Resolving a Resolved Spec is a no-op returning the same array — a Fieldset
  that has `children` is left alone. A Consumer can resolve from an effect
  keyed on the Spec without looping.

`specNeedsResolution(spec, adapters)` answers whether that call would fetch
anything — false for a Fieldset-free Spec, an already-Resolved Spec, or a
Consumer with no blueprint adapter. It is for a caller that renders
synchronously and only wants a loading state when there is something to wait
for (the editor's Preview mode uses it exactly that way); it never replaces
`resolveSpec()` — resolve on true, render as-is on false.

`children` is the resolved/not-resolved signal, and both `resolveSpec()` and
the component read it the same way: an authored Fieldset has no `children` key
at all, while a Blueprint with no Fields resolves to `[]` — resolved, and
displayed as "This blueprint has no fields" rather than fetched again.

Fields nested inside `settings` rather than `children` — a block's
`allowed_blocks[].fields`, for instance — are not walked, the same boundary
`validateSpec()` draws.

## Value Shape

One record under the Fieldset's Accessor. A Fieldset called `address` embedding
`street` and `city` submits:

```json
{ "address": { "street": "12 Bridge Lane", "city": "Ely" } }
```

The nesting is done by rewriting each child's Accessor to `address.street` —
the same mechanism that gives a Group row `authors.0.name`, with the index
omitted because a Fieldset holds one record rather than a list of them.

## Validation

**Resolved**, the record is the object its children describe: a required child
blocks submit, and its issue is reported at the child's own path
(`address.street`), so react-hook-form puts the message on the offending Field
rather than on the Fieldset. Nesting composes — a Fieldset inside a Fieldset
validates all the way down — and children obey the rules their top-level
siblings do: Markers and hidden Fields are skipped, optional children accept
the empty string (#38).

The record is `passthrough`, so keys the Blueprint's Fields don't describe — an
id, a hidden child's stored value — ride through the submit untouched. A
Blueprint says what the record's Fields are, not everything stored under it, and
validation arriving shouldn't start pruning the rest (ADR-0007). Group rows
follow the same rule.

**Unresolved**, it stays `z.record(z.unknown())`: nothing about the children is
checked, and the self-resolved Fields of path 2 are not rejected either —
failing a form over a Field fieldkit was never told about would be worse than
not checking it.

**`required` on the Fieldset itself** governs only whether the record has to be
there, resolved or not — a required *child* is what blocks submit. An optional
Fieldset is absent-or-complete: omit the key and it passes, supply the record
and its children are checked. In a form seeded by `getDefaultValues`
the key is always present, so this distinction shows up only for a Consumer
passing their own `defaultValues`.

This is the whole point of the resolve step, and the plugin contract that makes
it possible is additive: `toZodType` takes an optional second argument that
composes child Fields into an object schema (`ComposeChildrenSchema`), and every
plugin that ignores it is unchanged. `specToZodSchema`'s `overrides` are keyed
by top-level Accessor and are deliberately *not* applied to children — an
override for `street` means the Consumer's own Field, not one a Blueprint
happens to name the same.

## Default Value

The children's own defaults, composed into one record — a Fieldset embedding
`street` and `city` seeds `{ street: "", city: "" }`, nested Fieldsets
included. Unresolved, `{}`. Fresh per call either way, so no two forms share a
record.

## Table Cell

`FieldsetCell` renders the record's primitive values joined by `", "`, on the
same reasoning as `ListCell`: a column headed "Address" earns its place by
saying "12 Bridge Lane, Ely", not "2 fields". SpecForm's read mode uses the same
cell.

## Collapsing

A collapsible Fieldset **starts open**: a form user who cannot see a required
Field cannot fill it in, so folding is something they choose, not something the
form does to them. Collapsing hides the content with the `hidden` attribute
rather than unmounting it, so a collapsed Fieldset keeps its values and a submit
still carries them.

The disclosure is hand-rolled rather than Chakra's `Collapsible`, whose exit
animation never completes under jsdom — it leaves the content without `hidden`
and the trigger still reporting `aria-expanded="true"` after a close, which
would make both the collapse and its accessible state untestable.

## Known Limitations

- **Self-resolved children are not validated.** Only the resolved path reaches
  the Schema — see "Validation" above.
- **Nothing is deduplicated on the self-resolve path.** Two Fieldsets naming
  the same Blueprint make two `getSchema` calls. `resolveSpec()` fetches each
  Blueprint id once.
- **No cycle guard on the self-resolve path.** A Blueprint that transitively
  embeds itself resolves one level per nested render. Cycle detection lives in
  `resolveSpec()`.
- **Read mode summarises rather than expanding.** A resolved Group renders its
  rows as label/value pairs in read mode; a Fieldset renders its cell. Nothing
  needs the expanded form until Specs are routinely resolved.
- **A record of containers reads as empty in the cell.** Only primitive child
  values are summarised — a Fieldset whose children are all Groups or Lists
  shows the empty dash.
