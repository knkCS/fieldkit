# Blocks

Dynamic content zones with different block types. Each block has a `_type` discriminator and its own set of fields defined via `BlockDefinition`. Uses React Hook Form's `useFieldArray` for add/remove/reorder.

## When to Use

Use **Blocks** when content is heterogeneous — different items have different field structures (e.g., a page builder with text blocks, image blocks, and CTA blocks). For homogeneous repeating fields, use [Group](?path=/docs/fields-group--docs). For simple key-value pairs, use [Array](?path=/docs/fields-array--docs).

## Settings

| Setting          | Type                | Default | Description                        |
|------------------|---------------------|---------|------------------------------------|
| `allowed_blocks` | `BlockDefinition[]` | `[]`    | The block types available for use   |

### BlockDefinition

```ts
interface BlockDefinition {
  type: string;     // Unique block type identifier (stored as _type)
  name: string;     // Display name shown in the block picker
  fields: Field[];  // Child fields within this block type
}
```

## Validation

Each allowed type validates the fields it declares. A required field inside a
`heading` blocks submit and reports at `content.1.title` — the path
`NestedItemFields` registers it under, so the message lands on the offending
field inside the block (ADR-0007).

`_type` is applied after the declared fields, so a type declaring a field of
that accessor cannot overwrite the discriminator. Each branch stays
`passthrough`: a stored block carries keys its type doesn't declare — a backend
id, most obviously — and validation arriving is no reason to prune them.

A block type that declares no fields keeps the opaque block it always had, as
does `toZodType` called with a Field alone (no composer).

> Every stored block of every existing Blocks field is now checked, so a spec
> whose blocks were never validated can begin blocking submit on data that was
> already saved.

## Zod Output

```ts
// No allowed_blocks — any block with a _type string
z.array(z.object({ _type: z.string() }).passthrough())

// One allowed type — literal match, since discriminatedUnion needs 2+
z.array(z.object({ ...headingFields, _type: z.literal("heading") }).passthrough())

// Two or more — discriminated on _type, each branch composing its own fields
z.array(
  z.discriminatedUnion("_type", [
    z.object({ ...headingFields, _type: z.literal("heading") }).passthrough(),
    z.object({ ...imageFields, _type: z.literal("image") }).passthrough(),
  ]),
)
```

## Adding a Block

Choosing a type seeds the new block from the fields that type declares — each
field's explicit `config.default_value`, or its plugin's `defaultValue` where it
has one, exactly as `getDefaultValues` seeds the form itself (#38). A `heading`
of `title` and `pinned` starts `{ _type: "heading", title: "", pinned: false }`.

`_type` is written last, so a field declaring that accessor cannot overwrite the
discriminator that decides which fields render.

## Known Limitations

- A block type's fields live in `settings.allowed_blocks[].fields`, not in
  `children`, and only this plugin reaches into them. `resolveSpec()`,
  `validateSpec()` and `resolveMarkerConvention()` all walk `Field.children`
  only, so a Fieldset declared inside a block type is never resolved — it
  validates as the opaque record any unresolved Fieldset does, though the
  renderer still self-resolves it for display — and a duplicate accessor
  between two fields of one block type is never reported, the later one
  winning the composed shape.
- No drag-to-reorder — uses arrow buttons for moving blocks up/down
- No min/max block limits
- No per-block-type limits (e.g., max 1 hero block)
