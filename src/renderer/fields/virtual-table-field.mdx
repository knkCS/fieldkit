# Virtual Table

A repeating table of rows, one per record. Its **Row Spec** — the Spec every row follows — is declared in exactly one of two ways (ADR-0017):

- **Linked:** `settings.blueprint` names a Blueprint, resolved through the blueprint adapter as a Fieldset's is, so several Virtual Table Fields can share one Row Spec.
- **Embedded:** the Field's own `children` hold the Row Spec, as a Group's do — no adapter needed.

`validateSpec()` refuses a Field with both or neither. `resolveSpec()` turns a linked Row Spec into `children`, so the renderer, the table cell and the Schema all read one shape.

## When to Use

Use **Virtual Table** for a repeating set of records edited as a table rather than as stacked forms — a line-items table on an order, for example. Link the Row Spec when several Fields should share it; embed it when the Row Spec belongs to this Field alone. Available in every context: `availableIn: ["blueprint", "task", "form"]`.

## What a Row Spec may hold

**Only flat value Fields**, because each one must fit a table cell and a row drawer:

`text`, `textarea`, `markdown`, `number`, `date`, `time`, `boolean`, `select`, `radio`, `checkboxes`, `email`, `url`, `slug`, `color`, `lookup`, `media`, `single_reference`

No Markers (`section`, `card`) and no containers (`group`, `fieldset`, `blocks`, `array`, `list`, a nested `virtual_table`) — `validateSpec()` reports each offending Field with the `virtual_table_row_field_type` code. The list is exported from `/schema` as `VIRTUAL_TABLE_ROW_FIELD_TYPES`.

## Settings

| Setting                | Type     | Default | Description                                    |
|------------------------|----------|---------|------------------------------------------------|
| `blueprint`            | `string` | —       | Id of the Blueprint holding a **linked** Row Spec. Must not be set together with `children` |
| `always_latest`        | `boolean`| —       | Always fetch the latest schema version (currently unused) |
| `max_records_per_page` | `number` | `25`    | Rows shown per page. The table pages over the stored array — nothing is fetched |
| `min_items`            | `number` | —       | Fewest rows the table accepts (shared with `group` via `RowArrayCaps`) |
| `max_items`            | `number` | —       | Most rows the table accepts |

## Adapter Interface

A **linked** Row Spec is resolved through the `blueprint` adapter injected via `FieldKitProvider`. An **embedded** Row Spec needs no adapter at all:

```ts
blueprint: {
  getSchema: (blueprintId: string) => Promise<Field[]>;
  getData: (blueprintId: string, query: DataQuery) => Promise<DataPage>;
}
```

Where `DataQuery` and `DataPage` are:
```ts
interface DataQuery {
  page?: number;
  page_size?: number;
  sort_by?: string;
  sort_order?: "asc" | "desc";
}

interface DataPage<T = Record<string, unknown>> {
  items: T[];
  total: number;
  page: number;
  page_size: number;
}
```

**Note:** Only `getSchema` is called. `getData` is defined in the adapter interface but never invoked by the component — data comes from the form value, not the adapter.

The component reads its columns from `field.children` — the resolved Row Spec, whichever way it was declared. A Consumer who skipped `resolveSpec()` gets the Fieldset degrade path: the component self-resolves a linked Row Spec **for display only**, so the table has columns even though the Schema was built before those Fields existed.

## The table

The Field renders as anker's `DataTable`:

- **Columns** are the resolved Row Spec's Fields, each drawn by that Field Type's own `cellComponent` — the same cells `SpecDataTable` uses. A column whose Field is `hidden` is left out.
- **An actions column** carries *edit* and *delete* per row. It is not rendered at all in read mode.
- **Paging** is a slice of the Field's own array, `max_records_per_page` rows at a time. A row's position in the array — not its position on the page — is what edit and delete address, and deleting the last row of the last page falls back to the new last page.
- **Add row** appends; it disappears once `max_items` rows are stored, and *delete* disappears once only `min_items` are left — the same caps `group` honours.
- **A drag handle** per row, injected by anker when reordering is offered — that is, everywhere but read mode.

## Editing a row

"Add row" and "edit row" open a drawer that renders the Row Spec through fieldkit's **own renderer**, so every column brings its own control, its own Zod type and its own message — the drawer has no case for any Field Type.

The drawer edits a **draft**: its own form, seeded from the row and validated by the Row Spec's Schema. Saving writes the row into the Field's array value; cancelling writes nothing. Keys a row carries that no column edits — a backend id — survive a save, matching the `passthrough` in the row array's Zod type.

## Reordering rows

A row is dragged by its handle — pointer or keyboard, with dnd-kit's live-region
announcements — and the new order is written straight into the Field's array
value. The order the array is stored in *is* the order, so there is nothing else
to persist.

anker's `DataTable` stays controlled: it reports the move as `(fromIndex,
toIndex)` against the rows it was handed, which here is **one page** of the
array. Both indices are translated back to their place in the whole array before
the move is applied, so a drag on page two moves page two's rows. Moving a row
**across** pages is out of scope — anker's reorder only reaches rows that are
currently rendered.

Reordering is offered on every table this Field can edit and on none it cannot:
read mode passes no callback, so anker injects no handle column at all. Sorting
stays off on every column — a manual order and a sort order are two different
orders, and anker reports reorder indices against the unsorted `data`.

## Validation errors

A row's messages come from the Consumer's own parse, at the path the row array's Zod type reports (`line_items.1.quantity`):

- on the **row**, in an "Issue" column that appears only while some row has an error, naming the column and its message;
- in the **drawer**, on the column itself, so an invalid row opens with its error already showing rather than looking clean until the first save attempt.

A write re-runs validation only on a form that has already been submitted, so a fresh form does not report every empty required column before the Author has tried to save.

## Validation

An array of the row objects the resolved Row Spec describes. The rule is shared with `group` (`src/schema/row-array.ts`) — both hold an array of rows all shaped alike, and differ only in how a row is edited — so a wrong value type or a missing required Field blocks submit and reports at `line_items.1.quantity`. Rows are `passthrough`: a stored row carries keys the Row Spec does not edit (a backend id), and validating must not prune them.

An **unresolved** linked Row Spec keeps the opaque row — the Schema must not reject values for Fields fieldkit was never told about. "Resolved" is `children != null`, the same rule `resolveSpec()` and the renderer read.

`validateSpec()` takes an **authored** Spec: a Resolved linked Field names a Blueprint and holds children at once, which it reports as ambiguous. Validate before you resolve.

## Zod Output

```ts
// Resolved Row Spec (children != null)
z.array(composeChildren(children).passthrough())
  // .min(min_items) / .max(max_items) when set

// Row Spec not resolved (children == null)
z.array(z.record(z.unknown()))
```

## Table Cell

Renders a row count via `VirtualTableCell` (e.g. "5 rows", "1 row", "0 rows"). Shows an em-dash for null values.

## Known Limitations

- **No reordering across pages** — a row can only be dragged among the rows currently rendered, which is anker's own limit on `onRowReorder`. Moving a row to another page still means editing it there
- No sorting and no selection: the table is an editor over an ordered array, and sorting a stored order would lie about it — and would also break reordering, which addresses the unsorted array
- **The drag handle's label counts the page, the actions column counts the array** — anker labels a handle `Reorder row 2` by visible position, while *edit* and *delete* say `Edit row 4` by position in the array. On page two the two disagree
- Never fetches data from the adapter (`getData` is unused) — data must be provided as the form value
- `always_latest` is unused
- No settings editor yet: the editor offers no control for linking a Blueprint or authoring an embedded Row Spec
